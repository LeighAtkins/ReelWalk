ReelWalk in 3 minutes, with the hard problem

ReelWalkを3分で（苦労した点） · about 180 seconds

For "tell me more" or "what was hardest?". Product in one breath, architecture in four lines, then the real hard problem: a job lost on a worker crash (commit 1039f6c), the move to SQS (ADR 0001), and idempotent completion (ADR 0003). It ends with the gap that is still open, which shows judgement.

  1. ReelWalkについて、少し詳しくご説明します。

    Let me explain ReelWalk in a bit more detail.

  2. 物件の動画は、外注すると高く、自分で編集すると時間がかかります。

    Property videos are expensive to outsource and slow to edit yourself.

  3. そこで、スマホだけでリール動画を作れるアプリにしました。

    So I made an app that does the whole Reel on a phone.

  4. 特徴は、間取(まど)り図(ず)のマーカーが、映像に合わせて動くことです。

    Its signature feature is a floor-plan marker that moves in step with the video.

  5. 構成としては、Next.jsのWebアプリと、動画を作るワーカーを分けています。

    Architecturally, the Next.js web app and the rendering worker are separate.

  6. 書き出しは、CPUもメモリも多く使い、数分かかるからです。

    Rendering uses a lot of CPU and memory and can take minutes.

  7. Webは軽いままにして、ワーカーだけを増やせるようにしました。

    That keeps the web app light and lets me scale only the workers.

  8. プレビューと書き出しは、同じReactのコンポーネントで描いています。

    The preview and the export are drawn by the same React component.

  9. なので、スマホで見た映像と、書き出した動画がずれません。

    So what you see on the phone matches the exported video.

  10. ここからは、一番苦労した点をお話しします。

    Now let me talk about the hardest part.

  11. それは、書き出しのジョブを、確実に一回だけ完了させることでした。

    It was making sure each export job completes exactly once.

  12. 最初は、Redisのリストでジョブを渡していました。

    At first I passed jobs through a Redis list.

  13. ところが、ワーカーが処理中に落ちると、ジョブが消えてしまいました。

    But when a worker crashed mid-render, the job simply disappeared.

  14. そこで、SQSに切り替えました。

    So I switched to SQS.

  15. SQSは、受け取ったメッセージを一定時間、ほかから見えなくします。

    SQS hides a received message from other consumers for a set time.

  16. 時間内に削除されなければ、また別のワーカーに届きます。

    If it isn't deleted in time, it's delivered to another worker.

  17. ただし、同じメッセージが二回届く可能性があります。

    The catch is that the same message may arrive twice.

  18. なので、二回届いても結果は一つになるように、冪等性(べきとうせい)を持たせました。

    So I made the worker idempotent: two deliveries still give one result.

  19. 一つ目は、状態の更新を条件付きにしたことです。

    First, status updates are conditional.

  20. 「実行中のときだけ完了にする」ので、遅れた側は何も変えられません。

    "Mark done only if still running" means the late one changes nothing.

  21. 二つ目は、出力ファイルの名前をジョブIDで固定したことです。

    Second, the output file is named after the job ID.

  22. 二回作っても、同じファイルを上書(うわが)きするだけです。

    Rendering twice just overwrites the same file.

  23. 三つ目は、ハートビートです。20秒ごとに、DBに生存を書きます。

    Third, a heartbeat: every 20 seconds the worker writes to the database that it's alive.

  24. 60秒止まっていたら、別のワーカーが引き継ぎます。

    If it stops for 60 seconds, another worker takes over.

  25. 手動で再試行するときは世代番号を上げて、古いメッセージを捨てます。

    A manual retry bumps a generation number, so old messages are discarded.

  26. 3回失敗したら、デッドレターキューに移して、失敗として記録します。

    After three failures the message goes to a dead-letter queue and the job is marked failed.

  27. この判断は純粋(じゅんすい)な関数にして、Vitestでケースごとにテストしました。

    I made that decision logic a pure function and tested each case with Vitest.

  28. もう一つ、後から直した問題があります。

    There was one more problem that I fixed later.

  29. 最初は、ジョブの保存とメッセージの送信が、一つのトランザクションではありませんでした。

    At first, saving the job and sending the message weren't one transaction.

  30. 保存の直後にプロセスが落ちると、メッセージのないジョブが残ります。

    If the process died right after the save, a job was left with no message.

  31. そこで、トランザクショナル・アウトボックスを入れて、この隙間(すきま)を埋めました。

    So I added a transactional outbox and closed that gap.

  32. メッセージもジョブと一緒にDBに書いて、その後でキューに送ります。

    The message is written to the database together with the job, and sent to the queue afterwards.

  33. この経験から、失敗する前提で設計することを、強く意識するようになりました。

    This taught me to design on the assumption that things will fail.

To memorise: play it twice, shadow it once, then turn on Hide Japanese and say each line before tapping to check.
