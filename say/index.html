What it is

Phone in, Reel out.

  1. ReelWalkは、物件(ぶっけん)の写真から、スマホでリール動画を作るアプリです。

    ReelWalk makes Instagram Reels from property photos, on a phone.

  2. 特徴は、動画と一緒に動く、間取(まど)り図(ず)のマーカーです。

    Its special feature is a floor-plan marker that moves with the video.

  3. レストランも、メニューと自分の動画からリールを作れます。

    Restaurants can make Reels too, from their menu and their own clips.

  4. できた動画は、共有(きょうゆう)リンクで、どこでも見られます。

    A finished video can be shared with a link that works anywhere.

  5. 今は、reelwalking.comで本当に動いています。

    It's live today at reelwalking.com.

How it works

Web is the waiter, the queue is the order ticket, the worker is the kitchen.

  1. Webはウェイター、キューは注文票(ちゅうもんひょう)、ワーカーはキッチンです。

    The web app is the waiter, the queue is the order ticket, the worker is the kitchen.

  2. Webアプリは、動画を作りません。注文を受けるだけです。

    The web app never makes videos. It only takes the order.

  3. 正しい情報はデータベースだけ。キューにはIDしか入れません。

    The database is the only source of truth. The queue only carries an ID.

  4. 動画は、スマホからS3へ直接アップロードします。

    Videos upload straight from the phone to S3.

  5. 編集中は軽い720pのコピーを再生して、書き出しは元の動画を使います。

    While editing, the phone plays a light 720p copy; the export uses the original.

  6. プレビューと書き出しは同じ部品なので、見たままの動画になります。

    Preview and export use the same component, so what you see is what you get.

When things break

Twice is fine. Once is the result.

  1. メッセージは二回届くかもしれない、と考えて作りました。

    I designed it assuming a message can arrive twice.

  2. 二回動いても、結果は一つです。これが冪等性(べきとうせい)です。

    If it runs twice, there's still one result. That's idempotency.

  3. ワーカーが止まっても、二分ぐらいで別のワーカーが引(ひ)き継(つ)ぎます。

    If a worker dies, another one takes over within about two minutes.

  4. 三回失敗したら、ジョブは失敗になって、ユーザーがやり直せます。

    After three failures the job is marked failed, and the user can retry.

  5. ジョブとメッセージは、同じトランザクションで保存します。

    The job and its message are saved in the same transaction (an outbox).

  6. テストで90本作って、途中でワーカーを止めても、全部成功しました。

    In a load test, I made 90 videos and killed a worker midway. All 90 succeeded.

AWS and money

Built it big, measured it, rebuilt it small.

  1. 最初はEKSで一日動かして、それから請求額(せいきゅうがく)を見ました。

    First I ran it on EKS for a day, then I looked at the bill.

  2. ほとんど使わないのに、月250ドル。それは合いませんでした。

    $250 a month for something mostly idle. That didn't fit.

  3. 今はApp Runnerと、必要な時だけ動くFargateで、月10ドルから15ドルくらいです。

    Now it's App Runner plus Fargate only when needed: about $10 to $15 a month.

  4. 書き出しがない時は、サーバーは一台も動いていません。

    When nobody is exporting, no render server is running at all.

  5. その代わり、最初の書き出しは、始まるまで一、二分かかります。

    The trade-off: the first export after a quiet spell takes a minute or two to start.

  6. Kubernetesは、今もローカルのkindで、Argo CDと一緒に動いています。

    Kubernetes isn't gone: it still runs locally on kind, with Argo CD.

Shipping safely

Test, scan, then ship. No keys anywhere.

  1. 変更は全部、テストとスキャンをしてから出します。

    Every change is tested and scanned before it ships.

  2. AWSのリソースは、全部Terraformで管理しています。

    All the AWS resources are managed in Terraform.

  3. 本番にアクセスキーはありません。ロールだけです。

    There are no access keys in production, only roles.

  4. 見つかった脆弱性(ぜいじゃくせい)は、直すか、理由を書いて受け入れます。

    Each vulnerability found is either fixed, or accepted with a written reason.

  5. ルールはVitestで、画面の流れはPlaywrightで、本物の書き出しまで確かめます。

    Rules are tested with Vitest, and user flows with Playwright, right up to a real export.

Honest and forward-looking

Say what's done, say what's next.

  1. できたことと、まだのことを、はっきり分けて話します。

    I keep what's done and what's not done clearly separate.

  2. インスタへの直接投稿は作りましたが、まだMetaの開発モードです。

    Direct posting to Instagram is built, but it's still in Meta's development mode.

  3. AIツールも使いましたが、設計の判断は全部、文書に残しています。

    I used AI tools too, but every design decision is written down.

  4. 一番の学びは、測ってから選ぶことです。

    My biggest lesson: measure first, then choose.

  5. 次は、最初の書き出しを、もっと速くしたいです。

    Next, I want to make that first export start faster.

If they ask… say

  1. They ask

    なぜワーカーを分けたんですか。

    Why is the render worker separate?

  2. 動画作りは重くて時間がかかるので、Webと分けました。別々に増やせて、片方が落ちても大丈夫です。

    Rendering is heavy and slow, so it must never block the web app. They scale and fail separately.

  3. They ask

    なぜSQSですか。

    Why SQS?

  4. リトライとデッドレターキューが最初からあるからです。その代わり重複(ちょうふく)があるので、二回動いても大丈夫に作りました。

    Retries, a lease and a dead-letter queue come built in. The cost is duplicate messages, so the worker is idempotent.

  5. They ask

    途中でワーカーが落ちたら、どうなりますか。

    What if a worker crashes mid-render?

  6. ハートビートが止まって、二分後にメッセージが戻り、別のワーカーが続けます。三回だめなら失敗にして、ユーザーがやり直せます。

    Its heartbeat stops, the message comes back after two minutes, and another worker takes over. After three tries the job fails and the user can retry.

  7. They ask

    結果が二つにならないように、どうしていますか。

    How do you avoid two results for one job?

  8. 状態の更新に条件を付けて、ファイル名をジョブIDにしています。だから、結果は一つです。

    Status changes are conditional updates, the file is named after the job, and there's one output row per job.

  9. They ask

    なぜPostgreSQLとPrismaですか。

    Why PostgreSQL and Prisma?

  10. データ同士に関係があるからです。Prismaで、Webとワーカーが同じ型を使えます。

    The data is relational, and Prisma gives the web app and the worker one typed schema.

  11. They ask

    なぜServer ComponentsとServer Actionsですか。

    Why Server Components and Server Actions?

  12. 画面からそのままデータを読めて、更新は型のある関数です。別のAPIを作らなくていいからです。

    Pages read the database directly, and every change is a typed function checked with zod. No separate API to maintain.

  13. They ask

    なぜEKSをやめたんですか。

    Why did you stop using EKS?

  14. ちゃんと動きましたが、ほとんど使わないのに月250ドルでした。今は月10ドルから15ドルくらいです。

    It worked, but it cost about $250 a month for an app that's mostly idle. App Runner plus on-demand Fargate costs $10 to $15.

  15. They ask

    どうやってデプロイしていますか。

    How do you deploy?

  16. CIでテストとスキャンをして、コミットIDのタグでECRにイメージを送ります。本番はそのイメージを使います。

    CI tests and scans every change, then pushes images tagged with the commit to ECR. Production runs those images.

  17. They ask

    脆弱性(ぜいじゃくせい)には、どう対応していますか。

    How do you handle vulnerabilities?

  18. CIでTrivyがスキャンします。直すか、受け入れる理由を書いて残します。

    Trivy scans dependencies, config and images in CI. Each finding is fixed, or accepted with a written reason.

  19. They ask

    AIを使って作りましたか。

    Did you use AI to build it?

  20. はい、道具として使いました。設計の判断は全部書いてあって、一つずつ説明できます。

    Yes, as a tool. Every design decision is written down, and I can explain each one.

  21. They ask

    次に何を良くしたいですか。

    What would you improve next?

  22. 最初の書き出しを速くすること、キューの長さでワーカーを増やすこと、インスタ投稿を本番にすることです。

    A faster first export, scaling workers by queue length, and Instagram posting out of development mode.
