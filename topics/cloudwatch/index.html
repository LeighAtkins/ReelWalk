監視(かんし)（ログとメトリクス）

クラウドウォッチDesigned, not deployed

ログ、メトリクス、アラームで、システムの状態を見ます。

Logs, metrics and alarms show how the system is doing.

設計(せっけい)のみ Not wired up: web and worker log plain text to stdout and Kubernetes probes check health, but there is no CloudWatch agent, metric or alarm in the repo; everything CloudWatch-specific here is the plan.

How to explain it

  1. CloudWatchは、AWSの監視(かんし)サービスです。

    CloudWatch is AWS's monitoring service.

  2. ログ、メトリクス、アラームを1か所で見られます。

    Logs, metrics and alarms are in one place.

  3. 今のワーカーは、ジョブIDを付けてログを標準出力(ひょうじゅんしゅつりょく)に出しています。

    Today the worker logs to stdout with the job ID on each line.

  4. EKSでは、それをCloudWatch Logsに集める予定です。

    On EKS the plan is to collect that in CloudWatch Logs.

  5. 一番見たいのは、キューで一番古いメッセージの経過時間です。

    The key metric is the age of the oldest message in the queue.

  6. DLQにメッセージが入ったら、すぐアラームを出します。

    Any message in the DLQ raises an alarm right away.

  7. レンダー時間や失敗率も、メトリクスにしたいです。

    I'd also like render time and failure rate as metrics.

Why ReelWalk uses it

  1. 非同期処理は、止まっても画面ではすぐ気づけません。

    When async work stalls, you don't notice it on screen right away.

  2. なので、キューの滞留(たいりゅう)とDLQを見るのが一番効きます。

    So watching queue backlog and the DLQ gives the most value.

  3. ただ、ログやメトリクスを増やすと、コストも上がります。

    But more logs and metrics also means more cost.

Interview questions

本番では、何を監視(かんし)しますか？What would you monitor in production?

  1. まず、キューで一番古いメッセージの経過時間です。

    First, the age of the oldest message in the queue.

  2. これが伸びたら、ワーカーが足りないか止まっています。

    If it grows, workers are too few or stuck.

  3. 次に、DLQのメッセージ数です。1件でもアラームです。

    Next, DLQ message count. Even one is an alarm.

  4. あとは、レンダーの失敗率と時間です。

    Then render failure rate and duration.

ApproximateAgeOfOldestMessage beats queue length: it shows user-facing delay directly.

ワーカーが固まったら、どう気づきますか？How would you notice a stuck worker?

  1. ワーカーには、ヘルスチェックのエンドポイントがあります。

    The worker has a health check endpoint.

  2. ループが一定時間動かないと、503を返します。

    If the loop stops for a while, it returns 503.

  3. すると、Kubernetesが再起動します。

    Then Kubernetes restarts it.

  4. ジョブは、タイムアウト後に別のPodが引き継ぎます。

    The job is taken over by another pod after the timeout.

This part is real and runs on kind. Separate it clearly from the CloudWatch alarms, which are only planned.

ログは、どう改善したいですか？How would you improve the logs?

  1. 今はテキストなので、JSONの構造化(こうぞうか)ログにしたいです。

    They are plain text now; I'd move to structured JSON.

  2. ジョブID、世代、試行回数を項目にします。

    Job ID, generation and attempt become fields.

  3. そうすれば、CloudWatchで検索や集計ができます。

    Then CloudWatch can search and aggregate them.

Where it lives in ReelWalk

  • apps/worker/src/handler.ts

    Log lines prefixed with [jobId] for each decision and attempt.

  • apps/worker/src/index.ts

    /healthz returns 503 if the poll loop stops ticking.

  • infra/helm/reelwalk/templates/worker.yaml

    livenessProbe on /healthz; no readiness probe for a queue consumer.
