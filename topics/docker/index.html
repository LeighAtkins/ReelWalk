Docker

コンテナイメージ

ドッカーBuilt and running

アプリをDocker(ドッカー)イメージにして、どこでも同じ環境で動かします。

We package each app as a Docker image so it runs the same way everywhere.

実装済(じっそうず)み Real: the web and worker images build in CI on every push; on main they are pushed to GHCR and to ECR (GitHub OIDC role, no stored keys). App Runner and Fargate run the ECR images in production.

How to explain it

  1. デプロイする単位(たんい)ごとに、イメージを一つずつ作っています。

    We build one image per deployable unit.

  2. webはNext.jsで、workerは動画を書(か)き出(だ)すNodeのプロセスです。

    web is the Next.js app; worker is the Node process that renders videos.

  3. どちらもマルチステージビルドで、ビルド用と実行用を分けています。

    Both use multi-stage builds that separate the build stage from the runtime stage.

  4. webはNext.jsのstandalone出力で、必要なファイルだけをコピーします。

    web uses Next.js standalone output and copies only the files the server needs.

  5. workerにはChromeとffmpegが入っていて、MP4を書き出します。

    The worker image contains Chrome and ffmpeg, and renders MP4s.

  6. Chromeはビルド時にダウンロードするので、ポッドがすぐ動けます。

    Chrome is downloaded at build time, so a new pod can start working right away.

  7. 実行用イメージからは、npmなどのパッケージマネージャーを消(け)しています。

    The package managers such as npm are removed from the runtime images.

  8. 最後にUSER nodeで、root以外のユーザーとして動かします。

    Finally, USER node makes them run as a non-root user.

Why ReelWalk uses it

  1. デプロイ単位で分けると、それぞれ必要なものだけを入れられます。

    Splitting by deployable means each image holds only what it needs.

  2. workerはChromeを含むので重(おも)いですが、webは軽(かる)いままです。

    The worker is heavy because it contains Chrome, but web stays light.

  3. トレードオフは、Dockerfileが二つになり、管理が増えることです。

    The trade-off is two Dockerfiles to maintain.

Interview questions

イメージのサイズや安全性で、工夫したことはありますか？Did you do anything to keep the images small and safe?

  1. マルチステージで、ビルド用の道具を最終(さいしゅう)イメージに残しません。

    With multi-stage builds, no build tooling is left in the final image.

  2. workerは本番用(ほんばんよう)の依存(いぞん)だけをインストールしています。

    The worker installs production dependencies only.

  3. 使わないnpmやcorepackも、実行用イメージから消しました。

    I also removed npm and corepack, which are unused, from the runtime image.

  4. それで、Trivy(トリビー)のHIGHとCRITICALの指摘(してき)がなくなりました。

    That cleared Trivy's HIGH and CRITICAL findings.

  5. 最後に、rootではなくnodeユーザーで実行しています。

    And it runs as the node user, not root.

Give a concrete before/after: Trivy flagged the bundled npm, the pnpm store and old esbuild builds; removing them (commit c317ca1) cleared the image scan.

なぜwebとworkerで、イメージを分けたのですか？Why separate images for web and worker?

  1. 必要なものが、全然(ぜんぜん)違うからです。

    Because they need completely different things.

  2. workerはChromeとffmpegが必要で、イメージが重くなります。

    The worker needs Chrome and ffmpeg, which makes the image heavy.

  3. webにそれを入れると、デプロイも起動も遅(おそ)くなります。

    Putting that into web would slow down its deploys and startup.

  4. 分けておけば、別々(べつべつ)にスケールもできます。

    Kept apart, they can also scale independently.

Link it to the architecture: rendering runs in separate workers (ADR 0003), so the image split follows the process split.

コンテナを止めるとき、気をつけたことはありますか？Anything you were careful about when containers stop?

  1. workerは、tsxを直接(ちょくせつ)起動しています。

    The worker starts tsx directly.

  2. パッケージマネージャー経由(けいゆ)だと、SIGTERMが届(とど)かないからです。

    Through a package manager, SIGTERM would not reach it.

  3. SIGTERMを受けると、今の書き出しを終えてから止まります。

    On SIGTERM it finishes the current render, then stops.

  4. Kubernetes(クバネティス)の猶予(ゆうよ)時間は、300秒にしています。

    The Kubernetes grace period is set to 300 seconds.

Graceful shutdown is a classic follow-up. Mention terminationGracePeriodSeconds: 300 in the chart values.

Where it lives in ReelWalk

  • apps/web/Dockerfile

    Three stages: deps, builder, and a runner that copies only the standalone output and runs as node.

  • apps/worker/Dockerfile

    Chrome libraries and ffmpeg in the base, a --prod install, Chrome downloaded at build time, tsx started directly so SIGTERM arrives.

  • apps/web/next.config.ts

    output: "standalone" with the monorepo root as the tracing root.

  • .dockerignore

    Keeps node_modules, build output and local data out of the build context.
