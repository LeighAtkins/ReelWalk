EKS

マネージドなKubernetes(クバネティス)

イーケーエスBuilt and running

AWSが管理する、マネージドなKubernetes(クバネティス)です。

AWS's managed Kubernetes service.

実装済(じっそうず)み Built and retired: an EKS 1.34 cluster (Terraform, one t3.xlarge node, Pod Identity, RDS, ingress-nginx, cert-manager) ran reelwalking.com for one day on 2026-10-07 with a real render verified end to end, then was destroyed because it cost about $250 a month for an idle app (ADR 0014, superseded by ADR 0015).

How to explain it

  1. EKS(イーケーエス)は、Amazon Elastic Kubernetes Serviceの略です。

    EKS stands for Amazon Elastic Kubernetes Service.

  2. コントロールプレーンは、AWSが運用と冗長化(じょうちょうか)をします。

    AWS runs the control plane and makes it redundant.

  3. 私たちは、ノードとアプリに集中(しゅうちゅう)できます。

    We can focus on the nodes and the app.

  4. ReelWalkでは、同じHelmチャートをEKSで一日動かしました。

    In ReelWalk, I ran the same Helm chart on EKS for a day.

  5. ポッドには、Pod IdentityでAWSの権限(けんげん)を渡(わた)しました。

    Pods got AWS permissions through Pod Identity.

  6. ただ、月250ドルの大半(たいはん)が待機(たいき)コストだったので、やめました。

    But most of the $250 a month was idle cost, so I retired it.

  7. 静的(せいてき)なアクセスキーは使いません。

    No static access keys.

Why ReelWalk uses it

  1. コントロールプレーンを自分で運用するのは大変です。

    Running the control plane yourself is hard work.

  2. EKSなら、可用性(かようせい)やアップグレードをAWSに任(まか)せられます。

    With EKS, availability and upgrades are handled by AWS.

  3. 一方(いっぽう)で、コントロールプレーンだけでも費用がかかります。

    On the other hand, the control plane alone costs money.

  4. だから、まずkindで検証してから移(うつ)る順番にしました。

    So the order is: verify on kind first, then move.

Interview questions

EKSの運用経験はありますか？Do you have experience running EKS?

  1. 正直(しょうじき)に言うと、本番のEKSはまだ運用していません。

    To be honest, I have not run EKS in production yet.

  2. AWSアカウントの確認が終わらず、デプロイできませんでした。

    My AWS account verification never completed, so I could not deploy.

  3. 代わりに、同じチャートをローカルのkindで検証しました。

    Instead, I verified the same chart on a local kind cluster.

  4. EKS向けの差分(さぶん)は、values.yamlとIRSAの設計にまとめています。

    The EKS-specific differences are in values.yaml and the IRSA design.

  5. 入社後(にゅうしゃご)は、実際のクラスターで早くキャッチアップしたいです。

    After joining I want to catch up quickly on real clusters.

Do not bluff: the interviewer can probe node groups, upgrades and IRSA. An honest answer with a concrete plan scores better.

ポッドに、AWSの権限をどう渡しますか？How do pods get AWS permissions?

  1. IRSAを使う設計です。

    The design uses IRSA.

  2. サービスアカウントに、IAMロールのARNを付けます。

    The ServiceAccount is annotated with an IAM role ARN.

  3. ポッドは、短期間(たんきかん)の認証情報を自動でもらいます。

    Pods automatically receive short-lived credentials.

  4. アクセスキーを、Secretに入れる必要がありません。

    There is no need to put access keys into a Secret.

  5. values.yamlに、そのための設定欄(せっていらん)を用意しています。

    values.yaml already has a slot for that.

If they push further, mention EKS Pod Identity as the newer option, and least-privilege policies per workload.

EKSに移すとき、何が必要ですか？What would moving to EKS take?

  1. まず、TerraformでVPC、EKS、RDSなどを作ります。

    First, create the VPC, EKS, RDS and so on with Terraform.

  2. 次に、EKS用のvaluesファイルを用意します。

    Then prepare a values file for EKS.

  3. イメージは、CIからECRにプッシュします。

    CI pushes the images to ECR.

  4. チャートとアプリのコードは、変えない想定です。

    The chart and application code should not need changes.

  5. ただ、これはまだ検証していない仮説(かせつ)です。

    But that is an untested hypothesis.

ADR 0005 says exactly this: 'That claim is untested until it is done.'
