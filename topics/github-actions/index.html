GitHub Actions

CI/CDパイプライン

ギットハブアクションズBuilt and running

プッシュやプルリクエストのたびに、自動でテストとビルドをします。

It tests and builds automatically on every push and pull request.

実装済(じっそうず)み Real and green: lint, typecheck, unit tests, helm lint, Trivy scans, image builds and Playwright E2E run on every PR. On main the scanned images are pushed to GHCR and a release job commits the new image tag for Argo CD. The OIDC + ECR push steps exist but have never run because no AWS role is configured.

How to explain it

  1. CIは、GitHub Actions(ギットハブアクションズ)のワークフロー一つで動いています。

    CI is a single GitHub Actions workflow.

  2. プルリクエストと、mainへのプッシュで実行されます。

    It runs on pull requests and on pushes to main.

  3. 最初のジョブで、lint、型チェック、単体テストを実行します。

    The first job runs lint, typecheck and unit tests.

  4. 同じジョブで、Helmチャートもlintします。

    The same job lints the Helm chart.

  5. 別のジョブで、Trivy(トリビー)が依存関係(いぞんかんけい)と設定をスキャンします。

    A separate job has Trivy scan dependencies and configuration.

  6. webとworkerのイメージは、マトリックスで並列(へいれつ)にビルドします。

    The web and worker images build in parallel with a matrix.

  7. ビルドしたイメージも、Trivyでスキャンします。

    The built images are scanned with Trivy too.

  8. 最後に、Docker Composeでスタックを起動して、E2Eを流(なが)します。

    Finally, Docker Compose starts the stack and the E2E tests run.

Why ReelWalk uses it

  1. コードと同じリポジトリで、パイプラインを管理できます。

    The pipeline lives in the same repository as the code.

  2. 問題に、プルリクエストの段階(だんかい)で気(き)づけます。

    Problems are caught at the pull request stage.

  3. トレードオフは、E2Eに時間がかかることです。

    The trade-off is that E2E takes time.

  4. なので、E2Eはイメージのビルドと並列で走らせています。

    So E2E runs in parallel with the image builds.

Interview questions

CI/CDで、改善(かいぜん)したことはありますか？Have you improved CI/CD in any way?

  1. 単体テストのジョブで、E2Eが動いてしまう問題を直しました。

    I fixed the unit-test job accidentally running the E2E suite.

  2. e2eのスクリプト名がtestで、turboに拾(ひろ)われていました。

    The e2e package script was named test, so turbo picked it up.

  3. Dockerのレイヤーは、Actionsのキャッシュに保存しています。

    Docker layers are cached in the Actions cache.

  4. E2Eが失敗したら、ログとトレースを自動で保存します。

    When E2E fails, logs and traces are saved automatically.

  5. Trivyのバージョンは、一(いっ)か所(しょ)で固定(こてい)しています。

    Trivy's version is pinned in one place.

Tell one story with cause, fix and result. The turbo test-script collision (commit 1095187) is concrete and easy to explain.

AWSへの認証は、どうしていますか？How does CI authenticate to AWS?

  1. 長期間(ちょうきかん)のアクセスキーは、GitHubに置きません。

    No long-lived access keys are stored in GitHub.

  2. OIDCで、短期間のトークンをもらう設計です。

    The design gets a short-lived token via OIDC.

  3. そのため、ジョブにid-tokenの権限を付けています。

    That is why the job has the id-token permission.

  4. ただ、AWSのロールがまだないので、ECRへのプッシュは未実行(みじっこう)です。

    But there is no AWS role yet, so the ECR push has never run.

  5. 今は代(か)わりに、GHCR(ジーエイチシーアール)にプッシュしています。

    For now, the images go to GHCR instead.

  6. ジョブのトークンで認証するので、ここでも鍵(かぎ)は保存しません。

    It authenticates with the job's own token, so no key is stored there either.

Be explicit that the ECR push is wired but never executed (skipped until AWS_ROLE_ARN is set), and that the GHCR push is the one that really runs.

CDの部分は、どうなっていますか？What about the CD part?

  1. mainにマージすると、CIがイメージをGHCR(ジーエイチシーアール)にプッシュします。

    On a merge to main, CI pushes the images to GHCR.

  2. タグは、コミットのSHAです。

    The tag is the commit SHA.

  3. 次に、CIがそのタグをvaluesファイルに書いて、コミットします。

    Next, CI writes that tag into a values file and commits it.

  4. Argo CD(アルゴシーディー)がそのコミットを検知(けんち)して、クラスターに反映(はんえい)します。

    Argo CD detects that commit and applies it to the cluster.

  5. CIは、クラスターの認証情報を持ちません。

    CI holds no cluster credentials.

  6. ただ、動かしているのはローカルのkindで、EKSではまだです。

    But this runs on local kind, not on EKS yet.

CI and CD are both real now, but only against a local cluster. Say that scope plainly: the registry is GHCR, and ECR and EKS are designed.

Where it lives in ReelWalk

  • .github/workflows/ci.yml

    Jobs verify, dependency-scan, images (matrix web/worker, GHCR push on main), e2e and release; ECR push gated on vars.AWS_ROLE_ARN.

  • infra/helm/reelwalk/values-gitops.yaml

    Image repository and tag. The release job rewrites it with the commit SHA on every merge to main.

  • turbo.json

    The typecheck and test tasks that pnpm typecheck / pnpm test fan out across the workspace.

  • e2e/package.json

    Script renamed to e2e so turbo run test no longer launched the browser suite in the unit-test job.
