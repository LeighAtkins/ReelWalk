Helm

Kubernetes(クバネティス)のパッケージ管理

ヘルムBuilt and running

マニフェストを、テンプレートと値(あたい)でまとめるツールです。

It packages Kubernetes manifests as templates plus values.

実装済(じっそうず)み Real: the chart is linted in CI and installed on the local kind cluster with values-kind.yaml; values.yaml (the AWS defaults) has never been installed anywhere.

ExplainWhyWordsInterviewIn the repoWatch

How to explain it

  1. Helm(ヘルム)は、Kubernetes(クバネティス)のパッケージマネージャーです。

    Helm is the package manager for Kubernetes.

  2. パッケージのことを、チャートと呼(よ)びます。

    A package is called a chart.

  3. ReelWalkのチャートは、infra/helm/reelwalkにあります。

    ReelWalk's chart is in infra/helm/reelwalk.

  4. テンプレートは、web、worker、マイグレーションのJobです。

    The templates are web, worker and the migration Job.

  5. 環境ごとの違いは、valuesファイルに書きます。

    Per-environment differences go into values files.

  6. values.yamlは、AWS向けのデフォルトです。

    values.yaml holds the defaults for AWS.

  7. values-kind.yamlは、ローカルのkind用の上書(うわが)きです。

    values-kind.yaml overrides them for the local kind cluster.

  8. CIでは、両方の組(く)み合(あ)わせでhelm lintをかけます。

    CI runs helm lint against both combinations.

Why ReelWalk uses it

  1. 環境の差が、ファイル一つにはっきり出ます。

    The differences between environments show up clearly in one file.

  2. 環境が一つなら、素(す)のマニフェストやKustomizeでも十分です。

    With one environment, plain manifests or Kustomize would be enough.

  3. デメリットは、テンプレートの文法(ぶんぽう)が読みにくいことです。

    The downside is that template syntax is hard to read.

Interview questions

values.yamlとvalues-kind.yamlの違いは何ですか？What is the difference between values.yaml and values-kind.yaml?

  1. values.yamlは、本物のS3とSQSが前提(ぜんてい)です。

    values.yaml assumes real S3 and SQS.

  2. values-kind.yamlは、接続先(せつぞくさき)をMinIOとElasticMQに変えます。

    values-kind.yaml points the endpoints at MinIO and ElasticMQ.

  3. サービスはNodePortにして、localhost:8081で開けます。

    The Service becomes a NodePort, reachable on localhost:8081.

  4. ローカル用の、使(つか)い捨(す)ての認証情報(にんしょうじょうほう)もここです。

    The throwaway local credentials are there too.

  5. アプリのコードには、ローカル専用(せんよう)の分岐(ぶんき)がありません。

    The application code has no local-only branches.

Key message: the app always speaks the S3/SQS APIs; only configuration differs between environments.

設定を変えたとき、ポッドはどう更新されますか？How are pods updated when configuration changes?

  1. ConfigMapとSecretのチェックサムを、アノテーションに入れています。

    A checksum of the ConfigMap and Secret is put into an annotation.

  2. 設定が変わると、チェックサムも変わります。

    When the settings change, so does the checksum.

  3. するとポッドのテンプレートが変わり、ローリングアップデートが始まります。

    That changes the pod template, which triggers a rolling update.

envFrom values are read only at container start, so without this trick a config change would not reach running pods.

マイグレーションJobの名前に、ハッシュを付けたのはなぜですか？Why does the migration Job name include a hash?

  1. Jobのポッドテンプレートは、後から変更できないからです。

    Because a Job's pod template cannot be changed afterwards.

  2. 同じ名前のままだと、upgradeが失敗します。

    With the same name, the upgrade would fail.

  3. イメージタグとチャートのバージョンから、ハッシュを作ります。

    The hash comes from the image tag and chart version.

  4. だから、リリースごとに新しいJobができます。

    So each release creates a new Job.

Shows you have hit a real Kubernetes gotcha (immutable fields), not just read about Helm.

Where it lives in ReelWalk

  • infra/helm/reelwalk/values.yaml

    Defaults for a real cluster: AWS endpoints empty, secret.create false, IRSA annotation slot.

  • infra/helm/reelwalk/values-kind.yaml

    kind overrides: NodePort 30080, MinIO and ElasticMQ endpoints, throwaway credentials.

  • infra/helm/reelwalk/templates/_helpers.tpl

    Shared labels, the config checksum, and the non-root, read-only security contexts.

  • infra/helm/reelwalk/templates/migrate-job.yaml

    Job name hashed from the image tag and chart version.
