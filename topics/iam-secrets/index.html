IAM & Secrets

権限(けんげん)と秘密情報(ひみつじょうほう)

アイアム、シークレットBuilt and running

各ワークロードに、必要な権限だけをロールで渡します。

Each workload gets only the permissions it needs, through a role.

実装済(じっそうず)み Built: CI assumes an IAM role through GitHub OIDC to push to ECR (no stored keys); on EKS pods used Pod Identity; on App Runner and Fargate the instance and task roles carry the same scoped policy; credentials sit in SSM Parameter Store. Locally the Secret holds throwaway MinIO and Postgres credentials.

ExplainWhyWordsInterviewIn the repoWatch

How to explain it

  1. AWSの権限(けんげん)は、IAMロールで渡します。

    AWS permissions are granted with IAM roles.

  2. アクセスキーを、コンテナに入れないのが基本です。

    The rule is: no access keys inside containers.

  3. EKSでは、Pod IdentityかIRSAでPodにロールを付けます。

    On EKS, Pod Identity or IRSA attaches a role to a pod.

  4. Webはメッセージの送信、ワーカーは受信と削除だけです。

    The web app only sends messages; the worker only receives and deletes.

  5. これが、最小権限(さいしょうけんげん)の原則です。

    That is the principle of least privilege.

  6. DBのパスワードは、KubernetesのSecretで渡します。

    The database password is passed in a Kubernetes Secret.

  7. 本番では、そのSecretをチャートの外で管理します。

    In production that Secret is managed outside the chart.

  8. CIからAWSへは、OIDCで一時的(いちじてき)な認証情報(にんしょうじょうほう)を使います。

    From CI to AWS, OIDC provides temporary credentials.

Why ReelWalk uses it

  1. 長く使えるキーは、漏(も)れたときの被害が大きいです。

    Long-lived keys do a lot of damage if they leak.

  2. ロールなら、認証情報が自動で入れ替わります。

    With roles, credentials rotate automatically.

  3. ただ、今のチャートはServiceAccountが1つです。

    However, the chart currently has a single ServiceAccount.

  4. WebとワーカーでSAを分けるのが、次の改善点です。

    Splitting it between web and worker is the next improvement.

Interview questions

ワーカーには、どんな権限を付けますか？What permissions would the worker get?

  1. レンダー用のキューの、受信と削除と延長だけです。

    Only receive, delete and change-visibility on the render queue.

  2. S3は、決まったバケットの読み書きだけにします。

    S3 is limited to reading and writing one bucket.

  3. リソースはARNで指定して、ワイルドカードは避けます。

    Resources are named by ARN; wildcards are avoided.

  4. Webには、送信と署名付きURLの発行だけを付けます。

    The web app gets only send and presigned-URL signing.

Concrete actions (sqs:ReceiveMessage, sqs:DeleteMessage, sqs:ChangeMessageVisibility) show you have thought it through. This policy is live: it is attached to the Fargate task role and the App Runner instance role.

シークレットは、どう管理していますか？How do you manage secrets?

  1. ローカルのkindでは、使い捨ての値をSecretに入れています。

    On local kind, throwaway values go into a Secret.

  2. 本番では、チャートでは作らない設計です。

    In production the design is that the chart doesn't create it.

  3. Secrets Managerから、External Secretsで同期します。

    It would be synced from Secrets Manager with External Secrets.

  4. Gitには、秘密情報を一切入れません。

    No secrets ever go into Git.

IRSAとPod Identityの違いは何ですか？What's the difference between IRSA and Pod Identity?

  1. どちらも、PodにIAMロールを渡す仕組みです。

    Both give a pod an IAM role.

  2. IRSAは、OIDCプロバイダーとSAの注釈を使います。

    IRSA uses an OIDC provider and an annotation on the SA.

  3. Pod Identityは新しい方法で、設定が簡単です。

    Pod Identity is newer and simpler to set up.

  4. 新しいクラスタなら、Pod Identityを選びます。

    For a new cluster I'd choose Pod Identity.

The chart's comment mentions IRSA; either works. Saying you'd pick Pod Identity for new clusters shows current knowledge.
