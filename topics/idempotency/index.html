Q04

Idempotency

冪等性(べきとうせい)

べきとうせいBuilt and running

同じメッセージを何回処理しても、結果は1つになります。

However many times a message is processed, there is one result.

実装済(じっそうず)み Built and covered by Vitest handler tests (duplicate delivery, stale generation, take-over of a dead worker's job); exercised locally with ElasticMQ, never under production load. Per-claim fencing tokens are not implemented. The transactional outbox is built (ADR 0010) and tested against a real Postgres.

How to explain it

  1. SQSは、少なくとも一回(いっかい)届ける仕組みです。

    SQS delivers at least once.

  2. なので、同じメッセージが2回届くことがあります。

    So the same message can arrive twice.

  3. ワーカーが落ちたときも、同じジョブがまた届きます。

    When a worker dies, the same job arrives again too.

  4. そこで、何回処理しても結果が1つになるようにしました。

    So I made processing give one result no matter how many times it runs.

  5. 終わったジョブや、世代(せだい)が古いメッセージは消すだけです。

    Messages for finished jobs or an old generation are just deleted.

  6. ほかのワーカーが処理中なら、手を出さずに残します。

    If another worker is rendering it, the message is left alone.

  7. 出力のキーはジョブIDで決まるので、上書(うわが)きになります。

    The output key is derived from the job ID, so a rerun overwrites it.

  8. 出力の行もjobIdがユニークで、upsertで書きます。

    The output row has a unique jobId and is written with an upsert.

Why ReelWalk uses it

  1. ちょうど一回だけ届けるのは、分散(ぶんさん)システムでは難しいです。

    Exactly-once delivery is hard in a distributed system.

  2. 受け取る側を冪等(べきとう)にするのが、一番シンプルです。

    Making the receiver idempotent is the simplest answer.

  3. その代わり、まれに同じ動画を2回レンダーするコストは受け入れています。

    The trade-off: occasionally rendering the same video twice, which I accept.

Interview questions

メッセージの重複(ちょうふく)は、どう防いでいますか？How do you prevent duplicate messages?

  1. 防ぐのではなく、重複しても困らないようにしています。

    I don't prevent them; I make them harmless.

  2. 届いたら、まずDBのジョブの状態と世代を見ます。

    On arrival, the worker first checks the job's state and generation.

  3. もう終わっていれば、メッセージを消すだけです。

    If it is already done, it just deletes the message.

  4. 2回レンダーしても、出力は同じキーで、DBの行も1つです。

    Even if it renders twice, the output has the same key and there is one row.

Reframing 'prevent' as 'make harmless' is exactly what the interviewer hopes to hear for an at-least-once queue.

手動リトライのあとに、古いメッセージが届いたら？What if an old message arrives after a manual retry?

  1. リトライのたびに、世代(せだい)を1つ上げています。

    Each retry bumps the generation by one.

  2. メッセージにも、世代が入っています。

    The message carries a generation too.

  3. 世代が違えば、古いメッセージとして消します。

    If it doesn't match, it is deleted as stale.

  4. リトライ自体も条件付き更新なので、2回押しても1回分です。

    The retry itself is a conditional update, so tapping twice counts once.

まだ弱いところはありますか？Are there still weak spots?

  1. 落ちたと判断したワーカーが、実は生きている場合です。

    When a worker judged dead is actually still alive.

  2. そのとき、2つのワーカーが同じジョブを書き出せます。

    Then two workers can render the same job.

  3. 出力は同じなので、結果は壊れません。

    The output is the same, so the result isn't corrupted.

  4. 改善するなら、取るたびにトークンを発行してフェンシングします。

    To improve it, I'd issue a token per claim and fence writes with it.

  5. DB書き込みと送信の間も弱点でしたが、アウトボックスで埋めました。

    The gap between the DB write and the send was a weak spot too, but I closed it with an outbox.

Naming a real gap plus a concrete fix beats claiming perfection. Be clear the fencing token is an improvement, not built; the outbox is built (ADR 0010).
