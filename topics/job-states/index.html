Q03

Job state machine

ジョブの状態遷移(じょうたいせんい)

ジョブ ステートマシンBuilt and running

ジョブの状態と、許される変化を1つの表で決めています。

One table defines a job's states and which changes between them are allowed.

実装済(じっそうず)み Fully built: the transition table and its tests live in packages/core, and every status write in the worker and the Server Actions is a conditional Prisma updateMany on Postgres.

ExplainWhyWordsInterviewIn the repoWatch

How to explain it

  1. 状態は、QUEUED、RUNNING、SUCCEEDED、FAILEDの4つです。

    There are four states: QUEUED, RUNNING, SUCCEEDED and FAILED.

  2. 作られたらQUEUED、ワーカーが取ったらRUNNINGです。

    A new job is QUEUED; once a worker takes it, RUNNING.

  3. 成功したらSUCCEEDED、回数を使い切ったらFAILEDです。

    SUCCEEDED on success; FAILED when attempts run out.

  4. 失敗しても回数が残っていれば、QUEUEDに戻します。

    If an attempt fails with attempts left, it goes back to QUEUED.

  5. FAILEDからは、画面で手動リトライができます。

    From FAILED, the user can retry by hand in the UI.

  6. 許される遷移(せんい)は、packages/coreの表に書いてあります。

    The allowed transitions are written in a table in packages/core.

  7. 更新は、今の状態をWHEREに入れた条件付(じょうけんつ)き更新です。

    Each update is conditional, with the expected current state in the WHERE clause.

  8. 読んでから書くのではないので、競合(きょうごう)が起きません。

    It isn't a read followed by a write, so there is no race.

Why ReelWalk uses it

  1. 表にしておくと、全部の遷移をテストで確認できます。

    As a table, every transition can be checked in tests.

  2. 条件付き更新なら、ロックを長く持たずに排他(はいた)できます。

    Conditional updates give mutual exclusion without holding a lock for long.

  3. ただ、表と各WHERE句を、手で揃(そろ)えておく必要があります。

    The catch is that the table and each WHERE clause must be kept in step by hand.

Interview questions

2つのワーカーが同時に同じジョブを取ったら？What if two workers grab the same job at the same time?

  1. 取るときは、1つのUPDATE文で行います。

    Claiming is a single UPDATE statement.

  2. 条件は、QUEUEDで世代(せだい)が同じ、です。

    The condition is: QUEUED and the same generation.

  3. DBが順番に処理するので、更新できるのは1つだけです。

    The database applies them in turn, so only one succeeds.

  4. もう1つは更新件数が0なので、メッセージを残して終わります。

    The other updates zero rows, leaves the message and stops.

The key point is that the check and the write are one atomic statement, not SELECT then UPDATE.

なぜRUNNINGからQUEUEDに戻すんですか？Why go back from RUNNING to QUEUED?

  1. 自動リトライを待っている状態だからです。

    Because the job is waiting for an automatic retry.

  2. 画面でも、待っていることが分かります。

    The UI can show that it is waiting.

  3. 次のワーカーは、QUEUEDのジョブを普通に取れます。

    The next worker can claim a QUEUED job the normal way.

Mention that requeue also clears heartbeatAt, so a retried job never looks like it is still being rendered.

SUCCEEDEDのあと、状態は変わりますか？Can the state change after SUCCEEDED?

  1. 変わりません。終端状態(しゅうたんじょうたい)です。

    No. It is a terminal state.

  2. 遅れて届いたメッセージは、何もせずに消します。

    A message that arrives late is simply deleted.

  3. もう一度書き出すときは、新しいジョブを作ります。

    Exporting again creates a new job.

Where it lives in ReelWalk

  • packages/core/src/job-status.ts

    The TRANSITIONS table, canTransition and isTerminal.

  • apps/worker/src/store.ts

    claim, heartbeat, succeed, requeue and fail as conditional updateMany calls.

  • apps/web/app/actions.ts

    retryRenderJob: FAILED -> QUEUED and generation + 1 in one write.

  • packages/core/tests/job-status.test.ts

    Vitest tests for legal and illegal transitions.
