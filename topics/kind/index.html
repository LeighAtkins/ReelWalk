kind

ローカルのKubernetes(クバネティス)クラスター

カインドBuilt and running

Docker(ドッカー)のコンテナの中に、Kubernetes(クバネティス)クラスターを作るツールです。

It creates a Kubernetes cluster inside Docker containers.

実装済(じっそうず)み Real: infra/kind/up.sh creates the cluster, loads the images and installs the chart locally; kind is the stand-in for EKS, which was never created.

ExplainWhyWordsInterviewIn the repoWatch

How to explain it

  1. kind(カインド)は、Kubernetes in Dockerの略(りゃく)です。

    kind stands for Kubernetes in Docker.

  2. ノードが、Dockerのコンテナとして動きます。

    Each node runs as a Docker container.

  3. up.shで、クラスター作成からデプロイまで一回でできます。

    up.sh goes from creating the cluster to deploying in one run.

  4. kindのノードからはホストのイメージが見えないので、ロードします。

    kind nodes cannot see host images, so the script loads them in.

  5. Postgres、MinIO、ElasticMQは、チャートの外で起動します。

    Postgres, MinIO and ElasticMQ start outside the chart.

  6. 本番では、RDS、S3、SQSになるからです。

    Because in production they become RDS, S3 and SQS.

  7. ポートマッピングで、webをlocalhost:8081で開けます。

    A port mapping exposes web on localhost:8081.

Why ReelWalk uses it

  1. EKSは、最初の一時間からお金がかかります。

    EKS costs money from the first hour.

  2. 最初のポッドの前に、VPCやIAMの準備(じゅんび)も必要です。

    VPC and IAM work is also needed before the first pod.

  3. kindなら、数分で作って壊(こわ)せて、費用(ひよう)はゼロです。

    kind can be created and destroyed in minutes, at no cost.

  4. ただ、IRSAやロードバランサーなどは確認できません。

    But it cannot verify things like IRSA or load balancers.

Interview questions

なぜEKSではなく、kindを使ったのですか？Why kind instead of EKS?

  1. 目的は、Kubernetes(クバネティス)の運用を学んで、見せることでした。

    The goal was to learn and demonstrate operating Kubernetes.

  2. EKSは、費用と、VPCやIAMの準備がかかります。

    EKS costs money and needs VPC and IAM setup.

  3. kindなら無料(むりょう)で、すぐ作り直せます。

    kind is free and quick to recreate.

  4. AWSとの違いは、values-kind.yamlに集めています。

    The differences from AWS are collected in values-kind.yaml.

  5. ただ、EKSで本当に動くかは、まだ検証(けんしょう)していません。

    But I have not yet verified that it really runs on EKS.

Saying exactly what is not yet proven builds trust. ADR 0005 has the list.

kindでは確認できないことは何ですか？What can you not verify on kind?

  1. IRSAなど、本物のIAMの権限(けんげん)は確認できません。

    Real IAM permissions, such as IRSA.

  2. ロードバランサー、TLS、DNSもありません。

    There is no load balancer, TLS or DNS either.

  3. ノードの自動スケールも、対象外(たいしょうがい)です。

    Node autoscaling is also out of scope.

  4. RDSのネットワークやバックアップも同じです。

    Same for RDS networking and backups.

  5. これらは、EKSで初めて検証することになります。

    Those would first be verified on EKS.

A strong answer lists concrete gaps rather than saying 'it is basically the same'.

Where it lives in ReelWalk

  • infra/kind/cluster.yaml

    One control-plane node; maps NodePort 30080 to localhost:8081 and 30900 (MinIO) to 9100.

  • infra/kind/up.sh

    Idempotent bootstrap: create cluster, build and kind-load images, apply deps, helm upgrade --install.

  • infra/k8s/local/deps.yaml

    Postgres, MinIO and ElasticMQ as local stand-ins for RDS, S3 and SQS.

  • docs/adr/0005-local-kubernetes-before-eks.md

    Why kind first, and the list of what kind does not prove.
