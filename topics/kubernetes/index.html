Kubernetes

コンテナオーケストレーション

クバネティスBuilt and running

コンテナを宣言的(せんげんてき)に管理し、落(お)ちたら自動で戻(もど)します。

It manages containers declaratively and brings them back automatically when they fail.

実装済(じっそうず)み The Deployments, Service, probes, resources and migration Job are real: they run on a local kind cluster and ran on EKS for one day (ADR 0014) before production moved to App Runner and Fargate for cost (ADR 0015).

ExplainWhyWordsInterviewIn the repoWatch

How to explain it

  1. Kubernetes(クバネティス)は、コンテナをまとめて動かす基盤(きばん)です。

    Kubernetes is the platform that runs containers together.

  2. 一番小さい単位(たんい)は、ポッドです。

    The smallest unit is the Pod.

  3. webとworkerは、それぞれ別のデプロイメントです。

    web and worker are separate Deployments.

  4. webはレプリカ2つで、サービス経由(けいゆ)でアクセスします。

    web has two replicas and is reached through a Service.

  5. workerはキューから仕事を取るので、サービスはありません。

    The worker pulls work from the queue, so it has no Service.

  6. webには、/api/readyと/api/healthの二つのプローブがあります。

    web has two probes: /api/ready and /api/health.

  7. すべてのコンテナに、リクエストとリミットを設定しています。

    Every container has resource requests and limits.

  8. DBのマイグレーションは、リリースごとにJobで実行します。

    Database migrations run as a Job on each release.

Why ReelWalk uses it

  1. ReelWalkには、性質(せいしつ)の違うワークロードが三つあります。

    ReelWalk has three workloads with different needs.

  2. 止めずに更新するweb、数を増やすworker、一回だけのマイグレーションです。

    web that updates without downtime, workers that scale out, and a run-once migration.

  3. この規模(きぼ)なら、運用が楽なECSも十分(じゅうぶん)な選択肢(せんたくし)です。

    At this size ECS, which is easier to run, would also be a reasonable choice.

  4. それでも、同じマニフェストがローカルとEKSで動くので選びました。

    I still chose Kubernetes because the same manifests run locally and on EKS.

Interview questions

readinessとlivenessの違いは何ですか？What is the difference between readiness and liveness?

  1. livenessは、プロセスが生(い)きているかを見ます。

    Liveness checks whether the process is alive.

  2. 失敗すると、コンテナが再起動されます。

    If it fails, the container is restarted.

  3. readinessは、トラフィックを受けられるかを見ます。

    Readiness checks whether it can take traffic.

  4. 失敗しても、サービスから外(はず)されるだけです。

    If it fails, the pod is only taken out of the Service.

  5. ReelWalkでは、readinessだけがDBを確認します。

    In ReelWalk only readiness checks the database.

  6. DBが落ちても、再起動のループにならないためです。

    That way a database outage does not cause a restart loop.

The point they want: a dependency outage should remove pods from rotation, not restart them. /api/ready also returns 503 until the seed has run.

なぜKubernetes(クバネティス)を選んだのですか？Why did you choose Kubernetes?

  1. 性質の違うワークロードが、三つあったからです。

    Because there were three workloads with different needs.

  2. ローリングアップデート、スケール、Jobが全部そろっています。

    Rolling updates, scaling and Jobs are all built in.

  3. ECSのほうが運用は楽で、それも検討(けんとう)しました。

    ECS is easier to operate, and I considered it.

  4. ただ、同じチャートがkind(カインド)とEKSの両方で動きます。

    But the same chart runs on both kind and EKS.

  5. 今は、ローカルのkindで検証(けんしょう)しています。

    For now I have verified it on a local kind cluster.

Naming the alternative (ECS/Fargate) shows judgment, and the twist is that production ended up on Fargate after all: EKS ran for a day, cost about $250 a month, and was retired (ADR 0014, 0015). Kubernetes stays the local demo.

ダウンタイムなしで、どうデプロイしますか？How do you deploy without downtime?

  1. ローリングアップデートで、maxUnavailableを0にしています。

    A rolling update with maxUnavailable set to 0.

  2. 新しいポッドがreadyになってから、古いポッドを止めます。

    Old pods stop only after new ones are ready.

  3. マイグレーションは、Jobで実行します。

    Migrations run as a Job.

  4. readinessが、マイグレーションの完了(かんりょう)を待ちます。

    Readiness waits for the migration to finish.

  5. workerは、今の書き出しを終えてから止まります。

    Workers finish their current render before stopping.

Mention that migrations must stay backward compatible, because old and new pods run side by side during the rollout.

requestsとlimitsは、どう決めましたか？How did you set requests and limits?

  1. requestsは、スケジューリングの目安(めやす)です。

    Requests are what the scheduler uses to place pods.

  2. limitsは、メモリだけに付けています。

    Limits are set on memory only.

  3. CPUは、空(あ)いている時に使えるようにしています。

    CPU is left unlimited so pods can use spare capacity.

  4. workerはChromeを使うので、メモリを多めにしました。

    The worker gets more memory because it runs Chrome.

  5. ただ、値(あたい)は本番の計測(けいそく)ではなく、見積(みつ)もりです。

    But the values are estimates, not production measurements.

Memory over the limit means OOMKilled; CPU over a limit means throttling. Be clear the numbers are not from production load.

Where it lives in ReelWalk

  • infra/helm/reelwalk/templates/web.yaml

    web Deployment with maxUnavailable: 0, readiness on /api/ready, liveness on /api/health, plus the Service.

  • infra/helm/reelwalk/templates/worker.yaml

    worker Deployment: no Service, liveness on /healthz, /dev/shm in memory for Chrome, 300 s grace period.

  • infra/helm/reelwalk/templates/migrate-job.yaml

    The migration Job, named with a hash because a Job's pod template is immutable.

  • docs/adr/0004-kubernetes-and-helm.md

    Why Kubernetes, why the probe split, and the ECS alternative.
