Next.js

Webアプリの土台(どだい)

ネクストジェイエスBuilt and running

Next.jsのApp Routerで、画面とサーバー処理を一つのアプリにまとめています。

With the Next.js App Router, pages and server logic live in one app.

実装済(じっそうず)み Built with Next.js 16; runs locally (dev server, Docker Compose, kind) and in production on AWS App Runner at reelwalking.com (ADR 0015).

ExplainWhyWordsInterviewIn the repoWatch

How to explain it

  1. Next.js(ネクストジェイエス)は、Reactのフレームワークです。

    Next.js is a framework for React.

  2. ReelWalkでは、App Routerを使っています。

    ReelWalk uses the App Router.

  3. appフォルダの構成(こうせい)が、そのままURLになります。

    The structure of the app folder becomes the URLs.

  4. ページは基本的に、Server Componentsです。

    Pages are basically Server Components.

  5. 画面用のREST APIは作っていません。

    There is no REST API for the UI.

  6. データの更新は、すべてServer Actionsで行います。

    All data changes go through Server Actions.

  7. Route Handlerは、ヘルスチェックなど一部(いちぶ)だけです。

    Route Handlers are used only in a few places, like health checks.

  8. ビルドはstandalone出力(しゅつりょく)で、Dockerイメージを小さくしています。

    The build uses standalone output to keep the Docker image small.

Why ReelWalk uses it

  1. 画面とAPIを別々に作らなくていいので、コードが減(へ)ります。

    I don't have to build pages and an API separately, so there is less code.

  2. フルスタックを、一つのTypeScriptプロジェクトで書けます。

    The whole stack is one TypeScript project.

  3. トレードオフは、Next.js独自(どくじ)の約束事(やくそくごと)が多いことです。

    The trade-off is that Next.js has many conventions of its own.

  4. キャッシュの動きも、バージョンによってよく変わります。

    Caching behaviour also changes often between versions.

Interview questions

なぜNext.jsのApp Routerを選んだんですか？Why did you choose the Next.js App Router?

  1. 一番の理由は、Server ComponentsとServer Actionsです。

    The main reason is Server Components and Server Actions.

  2. ページの中で、直接(ちょくせつ)Prismaを呼べます。

    Pages can call Prisma directly.

  3. 更新もServer Actionsなので、UI用のAPIがいりません。

    Mutations are Server Actions too, so no API is needed for the UI.

  4. 一人で作るには、コードが少ないのが大事でした。

    Building it alone, having less code mattered a lot.

Tie the choice to a concrete benefit (no separate API layer). Craftsman uses Server Components/Actions too, so you can say you used them in a real app.

Route Handlerは、どこで使っていますか？Where do you use Route Handlers?

  1. 呼(よ)び出(だ)し元(もと)が、このアプリのUIじゃない時だけです。

    Only when the caller is not this app's UI.

  2. /api/healthと/api/readyは、Kubernetesのプローブ用です。

    /api/health and /api/ready are for Kubernetes probes.

  3. あとは、別のタイムラインエディター用のエンドポイントが一つです。

    Besides that, one endpoint for the separate timeline editor.

  4. それ以外は、すべてServer Actionsです。

    Everything else is a Server Action.

Shows you know when each tool fits: Server Actions for your own UI, Route Handlers for external callers.

パフォーマンスで工夫(くふう)したことはありますか？Did you do anything for performance?

  1. リール一覧(いちらん)のリンクは、プリフェッチを切っています。

    I turned off prefetch on the links in the reels list.

  2. エディターのページは重いので、全部のカードが先読(さきよ)みしていました。

    Editor pages are heavy, and every card was prefetching one.

  3. ブラウザの同時接続(どうじせつぞく)が埋(う)まって、次の操作が待たされたんです。

    That filled the browser's concurrent connections, and the next tap had to wait.

  4. 署名付(しょめいつ)きURLも、寿命(じゅみょう)の半分まで使い回(まわ)しています。

    Signed URLs are also reused for the first half of their lifetime.

  5. URLが変わると、ブラウザが動画を読み直すからです。

    Because if the URL changes, the browser reloads the video.

A real bug you found and fixed beats generic advice. Both are in the code (prefetch={false} in app/page.tsx, the signedUrls map in lib/storage.ts).

Where it lives in ReelWalk

  • apps/web/app/page.tsx

    The reels grid: an async Server Component that queries Prisma directly.

  • apps/web/app/api/health

    Route Handlers kept only for Kubernetes probes (health, ready) and the timeline editor.

  • apps/web/next.config.ts

    Standalone output and transpilePackages for the workspace packages.

  • apps/web/Dockerfile

    The web image built from the standalone output.
