Playwright

E2Eテスト

プレイライトBuilt and running

本物のブラウザで、ユーザーの操作(そうさ)を最後まで自動テストします。

It tests user flows end to end in a real browser.

実装済(じっそうず)み Real: the suite runs in CI against Docker Compose, including a real render to MP4; it can also point at the kind cluster via E2E_BASE_URL.

ExplainWhyWordsInterviewIn the repoWatch

How to explain it

  1. Playwright(プレイライト)は、ブラウザを自動で操作するテストツールです。

    Playwright is a test tool that drives a browser automatically.

  2. 本物のChromiumで、画面を操作してテストします。

    It operates the UI in a real Chromium.

  3. ReelWalkはスマホ向けなので、Pixel 7の画面サイズで実行します。

    ReelWalk is for phones, so tests run at a Pixel 7 viewport.

  4. メインのテストは、写真と動画からリールを作ります。

    The main test makes a reel from photos and a video.

  5. 最後に本当に書き出して、MP4が取れるかを確認します。

    Then it really renders and checks the MP4 can be fetched.

  6. 壊れた動画で、リトライ後に失敗する流れもテストします。

    A corrupt video tests failing after retries.

  7. CIでは、Docker Composeで全部のサービスを起動して流します。

    In CI, Docker Compose starts every service and the suite runs.

  8. ローカルでは、並列数(へいれつすう)を2にしています。

    Locally, parallelism is set to 2.

Why ReelWalk uses it

  1. 単体テストでは、サービス間(かん)のつながりを確認できません。

    Unit tests cannot check how the services connect.

  2. E2Eなら、web、キュー、worker、S3まで通(とお)して確認できます。

    E2E checks the whole path: web, queue, worker and S3.

  3. トレードオフは、遅くて不安定(ふあんてい)になりやすいことです。

    The trade-off is that they are slow and prone to flakiness.

  4. なので、CIでは一回だけリトライして、トレースを残します。

    So CI retries once and keeps traces.

Interview questions

E2Eテストでは、何を確認していますか？What do your E2E tests check?

  1. ユーザーの流れを、ブラウザで最初から最後まで通します。

    They run user flows in the browser from start to finish.

  2. リールを作って、編集して、書き出すまでです。

    Making a reel, editing it and exporting it.

  3. 書き出しは本物で、workerがMP4を作ります。

    The render is real: the worker produces an MP4.

  4. MP4の形式で、50KBより大きいことも確認します。

    It checks the file is MP4 and larger than 50 KB.

  5. 失敗のケースは、壊れた動画で確認しています。

    Failure cases use a corrupt video.

Stress 'no mocks': the E2E goes through SQS (ElasticMQ), the worker, Chrome and S3 (MinIO).

なぜローカルでは、ワーカー数を2にしたのですか？Why two workers locally?

  1. 5並列だと、リクエストがちょうど10秒ずつ止まりました。

    With five in parallel, requests stalled in exact 10-second steps.

  2. MinIOに直接送っても同じで、アプリの問題ではありませんでした。

    It happened even straight to MinIO, so it was not the app.

  3. WindowsからDocker Desktopへの通信で起きていました。

    It happened between the Windows host and Docker Desktop.

  4. LinuxのCIでは起きないので、ローカルだけ2にしました。

    Linux CI is unaffected, so only local runs use 2.

  5. 根本原因(こんぽんげんいん)は、まだ調査中(ちょうさちゅう)です。

    The root cause is still under investigation.

A good debugging story: you isolated the layer (原因の切り分け) before blaming the app. Don't claim a root cause you haven't found.

フレーキーなテストを、どう防(ふせ)ぎますか？How do you prevent flaky tests?

  1. 固定の待ち時間ではなく、状態を待ちます。

    Wait for state, not for a fixed time.

  2. 例えば、data-statusがSUCCEEDEDになるまで待ちます。

    For example, wait until data-status becomes SUCCEEDED.

  3. 要素は、data-testidやロールで探(さが)します。

    Elements are found by data-testid or role.

  4. CIでは一回だけリトライして、失敗時はトレースを残します。

    CI retries once and keeps a trace on failure.

Retries hide flakiness if overused; one retry plus a trace to investigate is a reasonable balance.

Where it lives in ReelWalk

  • e2e/playwright.config.ts

    Pixel 7 project, 5-minute timeout, 2 workers by default (the Windows 10 s stall note), 1 retry and traces on CI.

  • e2e/tests/reels.spec.ts

    Create, edit and export a reel; Instagram limits; conflict between tabs; corrupt video fails then retries.

  • e2e/fixtures/corrupt.mp4

    A file that passes upload checks but cannot be decoded, to drive the retry and DLQ path.
