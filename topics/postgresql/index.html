データの正(せい)はPostgreSQLで、状態は条件付(じょうけんつ)きUPDATEで変えます。

PostgreSQL is the source of truth, and state changes are conditional UPDATEs.

実装済(じっそうず)み Built: PostgreSQL 16 runs locally in Docker Compose and kind; production used RDS for a day (ADR 0014) and now uses the free Postgres tier at Supabase (ADR 0015). The conditional updates are real and tested.

How to explain it

  1. データの正(せい)は、PostgreSQLに置いています。

    PostgreSQL holds the source of truth.

  2. リール、メディア、ジョブ、出力(しゅつりょく)が全部入っています。

    Reels, media, jobs and outputs are all in it.

  3. キューのメッセージは、ジョブIDと世代(せだい)だけです。

    Queue messages carry only the job ID and its generation.

  4. 状態は、いつもDBの行(ぎょう)を見て判断(はんだん)します。

    State is always decided by looking at the DB row.

  5. ステータスの変更は、条件付(じょうけんつ)きのUPDATE一回です。

    A status change is a single conditional UPDATE.

  6. WHERE句(く)に、今のステータスと世代を入れます。

    The WHERE clause includes the current status and generation.

  7. 誰かが先に更新していたら、0行になるだけです。

    If someone updated it first, zero rows change, that's all.

  8. 読んでから書く処理がないので、ロックはいりません。

    There's no read-then-write, so no locks are needed.

Why ReelWalk uses it

  1. データがリレーショナルで、ジョインが必要だからです。

    Because the data is relational and needs joins.

  2. DynamoDBも考えましたが、アクセスパターンがまだ固(かた)まっていませんでした。

    I considered DynamoDB, but the access patterns weren't settled yet.

  3. AWSではRDSを使う設計で、変わるのはDATABASE_URLだけです。

    The AWS design uses RDS; only DATABASE_URL changes.

  4. トレードオフは、接続数(せつぞくすう)やスケールを自分で考える必要があることです。

    The trade-off is having to think about connection counts and scaling yourself.

Interview questions

二つのワーカーが同じジョブを取ったら、どうなりますか？What happens if two workers pick up the same job?

  1. 両方(りょうほう)がupdateManyで、RUNNINGにしようとします。

    Both try to set it to RUNNING with updateMany.

  2. WHEREには、QUEUEDか、ハートビートが古いRUNNINGを入れています。

    The WHERE accepts QUEUED, or RUNNING with a stale heartbeat.

  3. 先に書いた方だけが、1行更新できます。

    Only the one that writes first updates one row.

  4. もう一方(いっぽう)は0行なので、何もしません。

    The other gets zero rows, so it does nothing.

  5. DBが判定(はんてい)するので、アプリ側でロックはいりません。

    The DB decides, so the app needs no lock.

This is the core of the design. Draw it on paper if there's a whiteboard: WHERE status/generation is the guard.

トランザクションは使っていますか？Do you use transactions?

  1. 完了(かんりょう)の時は、出力の保存とステータス更新を一つのトランザクションにしています。

    On completion, saving the output and updating the status are one transaction.

  2. ただ、DBとキューは別のシステムなので、一つのトランザクションにはできません。

    But the database and the queue are separate systems, so they can't share one transaction.

  3. そこで、Outboxパターンを使っています。

    So I use the outbox pattern.

  4. ジョブと同じトランザクションで、メッセージをDBのテーブルに書きます。

    In the same transaction as the job, I write the message to a table in the database.

  5. コミットの後で、そのテーブルからキューに送ります。

    After the commit, it is sent from that table to the queue.

  6. 送信に失敗しても、メッセージはDBに残るので、後でもう一度送れます。

    If the send fails, the message stays in the database, so it can be sent again later.

Know the why: the DB and the queue can't share a transaction, so the message goes into the DB first (ADR 0010). The relay can send twice, which the idempotent worker already handles.

本番(ほんばん)のデータベースは、どうしていますか？What do you do for the database in production?

  1. 最初は、TerraformでRDSのPostgreSQLをプライベートサブネットに作りました。

    At first I created RDS PostgreSQL in private subnets with Terraform.

  2. 一日動かして、EKSごとコストの判断でやめました。

    It ran for a day, and I retired it along with EKS over cost.

  3. 今は、AWSの外の無料枠(むりょうわく)のPostgreSQLを使っています。

    Now I use a free PostgreSQL tier outside AWS.

  4. ローカルでは、同じPostgreSQL 16で動かしています。

    Locally it runs on the same PostgreSQL 16.

RDS was real for one day (ADR 0014). Say why it went: $15 a month for an idle database when a free tier does the job (ADR 0015). Mention the one surprise: RDS 16 forces TLS, so the connection string needs sslmode.
