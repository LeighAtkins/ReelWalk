S3

オブジェクトストレージ

エススリーRuns locally with a stand-in

素材(そざい)と書(か)き出(だ)した動画を置く場所で、ブラウザは署名付(しょめいつ)きURLで直接アップロードします。

Where uploads and rendered videos live; the browser uploads straight to it with presigned URLs.

ローカルで検証(けんしょう) The code uses the AWS SDK v3 S3 client and presigned URLs, but it has only run against MinIO (Docker Compose and kind); the S3 bucket and CloudFront exist only in the Terraform sketch.

How to explain it

  1. S3は、AWSのオブジェクトストレージです。

    S3 is AWS's object storage.

  2. アップロードした素材(そざい)と、書(か)き出(だ)したMP4を置いています。

    It holds uploaded media and the exported MP4s.

  3. ブラウザは、S3に直接アップロードします。

    The browser uploads directly to S3.

  4. サーバーは、署名付(しょめいつ)きURLを発行(はっこう)するだけです。

    The server only issues a presigned URL.

  5. アップロード用のURLは、10分で期限(きげん)が切れます。

    The upload URL expires after 10 minutes.

  6. その後、HeadObjectで本当にあるか確認します。

    Then HeadObject checks that the file is really there.

  7. 再生(さいせい)とダウンロードには、署名付きのGET URLを使います。

    Playback and downloads use presigned GET URLs.

  8. ローカルでは、MinIOがS3の代わりをしています。

    Locally, MinIO stands in for S3.

Why ReelWalk uses it

  1. 2GBの動画を、Next.jsのメモリに通したくないからです。

    Because I don't want 2 GB videos passing through Next.js memory.

  2. コードはAWS SDKのままで、エンドポイントだけ切(き)り替(か)えます。

    The code stays on the AWS SDK; only the endpoint changes.

  3. トレードオフは、URLの署名とエンドポイントの設定が少しややこしいことです。

    The trade-off is that URL signing and endpoint settings get a bit fiddly.

  4. サーバー内部(ないぶ)の宛先(あてさき)と、ブラウザから見える宛先が違うからです。

    Because the in-cluster address differs from the one the browser can reach.

Interview questions

なぜブラウザから直接アップロードするんですか？Why upload directly from the browser?

  1. 動画は最大(さいだい)2GBあります。

    Videos can be up to 2 GB.

  2. Webサーバーのメモリを通す理由がありません。

    There's no reason to pass them through the web server's memory.

  3. Server Actionsには、ボディサイズの制限(せいげん)もあります。

    Server Actions also have a body size limit.

  4. なので、サーバーは検証(けんしょう)して、署名付(しょめいつ)きURLを返すだけです。

    So the server only validates and returns a presigned URL.

  5. アップロード後に、HeadObjectで存在(そんざい)を確認してから登録します。

    After the upload, it confirms the object with HeadObject before recording it.

Mention the two-step flow (createUpload, then confirmUpload). The server never decodes media; the browser measures duration and makes the thumbnail.

署名付きURLで、ハマったことはありますか？Any gotchas with presigned URLs?

  1. はい、いくつかありました。

    Yes, a few.

  2. まず、署名はブラウザから見えるホスト名で作る必要があります。

    First, the signature must be made for the host the browser can reach.

  3. なので、サーバー用と署名用で、クライアントを二つ作りました。

    So I made two clients: one for server calls, one for signing.

  4. 次に、SDKのチェックサムヘッダーを、ブラウザは送れません。

    Next, the browser can't send the SDK's checksum headers.

  5. 最後に、同じキーでも署名のたびにURLが変わって、動画が読み直されました。

    Finally, each signing gives a new URL, which made videos reload.

Specific war stories show you really built it. All three fixes are in apps/web/lib/storage.ts.

AWSのS3は、実際(じっさい)に使いましたか？Did you actually use AWS S3?

  1. はい、本番は本物のS3とCloudFrontで動いています。

    Yes, production runs on real S3 and CloudFront.

  2. バケットはTerraformにインポートして、CORSと暗号化(あんごうか)を追加しました。

    I imported the bucket into Terraform and added CORS and encryption.

  3. ローカルではMinIOを使って、同じAWS SDKで動かしています。

    Locally I use MinIO, with the same AWS SDK.

  4. 切り替えは、環境変数(かんきょうへんすう)を変えるだけです。

    Switching is just a change of environment variables.

Honesty is the point here. Then pivot to what you did verify locally.

Where it lives in ReelWalk

  • apps/web/lib/storage.ts

    Presigned PUT/GET, HeadObject, separate in-cluster and public endpoints, and the signed-URL reuse cache.

  • packages/core/src/keys.ts

    Object key layout: uploads/, thumbs/, and renders/<jobId>.mp4 for idempotent output.

  • apps/web/components/editor/upload.ts

    The browser side: PUTs the file and thumbnail straight to storage.

  • docker-compose.yml

    MinIO (Chainguard image) and ElasticMQ as local stand-ins.
