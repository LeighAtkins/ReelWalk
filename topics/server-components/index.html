Server Components

サーバーで描画(びょうが)する部品

サーバーコンポーネントBuilt and running

データ込みでサーバーで描画(びょうが)し、操作する部分だけをクライアントにします。

Render on the server with the data included; only the interactive parts go to the client.

実装済(じっそうず)み Built: the reels grid, editor page, export screen and exports list are async Server Components reading Postgres through Prisma; running locally and in production.

ExplainWhyWordsInterviewIn the repoWatch

How to explain it

  1. Server Componentsは、サーバーだけで動くコンポーネントです。

    Server Components are components that run only on the server.

  2. async関数として書けて、中でPrismaを直接(ちょくせつ)呼べます。

    They can be async functions and call Prisma directly.

  3. ブラウザにJavaScriptを送らないので、軽いです。

    They send no JavaScript to the browser, so they are light.

  4. 一方(いっぽう)、Client Componentsはブラウザで動きます。

    Client Components, on the other hand, run in the browser.

  5. stateやイベントが必要なら、「use client」を付けます。

    If you need state or events, you add "use client".

  6. エディターのページが、いい例(れい)です。

    The editor page is a good example.

  7. サーバーでリールとメディアを読んで、propsで渡します。

    The server loads the reel and its media and passes them as props.

  8. 編集の操作は、Client ComponentのEditorが担当(たんとう)します。

    The editing itself is handled by the Editor Client Component.

Why ReelWalk uses it

  1. データ取得(しゅとく)のためのAPI層(そう)が、いらなくなります。

    There is no need for an API layer just to fetch data.

  2. DBの接続情報(せつぞくじょうほう)が、ブラウザに出ることもありません。

    DB connection details never reach the browser.

  3. トレードオフは、境界(きょうかい)を意識(いしき)する必要があることです。

    The trade-off is that you have to keep the boundary in mind.

  4. 渡せるpropsは、シリアライズできる値だけです。

    Only serializable values can be passed as props.

Interview questions

Server ComponentsとClient Componentsの違いは何ですか？What's the difference between Server and Client Components?

  1. Server Componentsは、サーバーだけで実行されます。

    Server Components run only on the server.

  2. DBに直接アクセスできて、JSはブラウザに送られません。

    They can access the DB directly, and no JS is sent to the browser.

  3. Client Componentsは、ブラウザでも動きます。

    Client Components also run in the browser.

  4. stateやクリックなどの操作が必要な時に使います。

    I use them when I need state or interactions like clicks.

  5. ReelWalkでは、データはサーバー、操作はクライアントと分けています。

    In ReelWalk, data stays on the server and interaction on the client.

Give the rule and then one concrete example from your app (editor page loads data, Editor is the client component).

レンダリングの進捗(しんちょく)は、どうやって画面に出していますか？How do you show render progress on screen?

  1. ワーカーが進捗を、PostgreSQLに直接書きます。

    The worker writes progress straight to PostgreSQL.

  2. 画面はServer Componentなので、DBの値をそのまま表示(ひょうじ)します。

    The page is a Server Component, so it just shows the DB value.

  3. ジョブが動いている間だけ、2秒ごとにrouter.refreshを呼びます。

    Only while a job is running, it calls router.refresh every 2 seconds.

  4. クライアント側(がわ)に、データ取得(しゅとく)の仕組(しく)みはいりません。

    No data-fetching layer is needed on the client.

Polling via router.refresh is simple and honest. If asked about WebSockets or SSE, say it would be the next step at higher scale.

どこまでをClient Componentにしましたか？How much did you make into Client Components?

  1. できるだけ小さくしています。

    As little as possible.

  2. エディター、共有(きょうゆう)ボタン、タブバーなど、操作がある部分だけです。

    Only interactive parts: the editor, the share button, the tab bar and so on.

  3. 一覧(いちらん)や書(か)き出(だ)し画面は、Server Componentです。

    The lists and the export screen are Server Components.

"Push the client boundary down" is the standard best practice; say it in your own words.

Where it lives in ReelWalk

  • apps/web/app/reels/[id]/page.tsx

    Server Component loads the reel, library and floor plans, then renders the client Editor.

  • apps/web/components/editor/editor.tsx

    The "use client" boundary: the interactive editor.

  • apps/web/components/auto-refresh.tsx

    Tiny client component that calls router.refresh() every 2 s while a render is active.

  • apps/web/lib/workspace.ts

    getCurrentUser wrapped in React cache(), so one request queries the user once.
