Q01

SQS

ジョブの待ち行列(ぎょうれつ)

エスキューエスRuns locally with a stand-in

Webからワーカーへ、レンダーの仕事を渡すキューです。

The queue that hands render jobs from the web app to the workers.

ローカルで検証(けんしょう) The code uses the real AWS SDK SQS client against ElasticMQ locally (Docker Compose and kind) and against SQS in production, where Terraform creates the queue and its dead-letter queue with the same lease and receive count (ADR 0011, 0015).

How to explain it

  1. 動画のレンダーは、数分かかることがあります。

    Rendering a video can take several minutes.

  2. なので、Webのリクエストの中では処理しません。

    So we don't do it inside a web request.

  3. WebはジョブをDBに書いてから、SQSにメッセージを送ります。

    The web app writes the job to the database, then sends a message to SQS.

  4. メッセージの中身は、jobIdとgenerationだけです。

    The message carries only the jobId and the generation.

  5. ワーカーはロングポーリングで、最大10秒待って受け取ります。

    Workers receive with long polling, waiting up to 10 seconds.

  6. 受け取ったメッセージは、可視性(かしせい)タイムアウトの間、見えなくなります。

    A received message stays invisible for the visibility timeout.

  7. これが実質的(じっしつてき)に、ジョブのリースになります。

    That effectively works as a lease on the job.

  8. ローカルでは、ElasticMQで同じAPIを使っています。

    Locally, ElasticMQ provides the same API.

Why ReelWalk uses it

  1. 最初はRedisのリストで、ワーカーが落ちるとジョブが消えていました。

    The first version used a Redis list, and a job was lost whenever a worker died.

  2. SQSなら、可視性(かしせい)タイムアウトとDLQが最初からあります。

    SQS has a visibility timeout and a dead-letter queue out of the box.

  3. その代わり、届くのは「少なくとも一回(いっかい)」なので、重複(ちょうふく)対策が必要です。

    The trade-off is at-least-once delivery, so duplicates have to be handled.

  4. Postgresをキューにする案もありましたが、長いレンダーとは相性が悪いです。

    Using Postgres as a queue was an option, but it fits poorly with long renders.

Interview questions

なぜSQSを選んだんですか？Why did you choose SQS?

  1. レンダーは長くて、途中でプロセスが落ちることもあります。

    Renders are long and the process can die halfway.

  2. 最初のRedisのリストだと、そのときジョブが消えていました。

    With the first Redis list, the job was lost when that happened.

  3. SQSは可視性(かしせい)タイムアウトで、落ちても再配信(さいはいしん)されます。

    With SQS the visibility timeout means the job is redelivered after a crash.

  4. 受信回数とDLQも、自分で作る必要がありません。

    I don't have to build receive counts or a DLQ myself.

They want a reason tied to failure handling, not 'it is the AWS default'. Mention the Redis LPOP version you replaced.

可視性(かしせい)タイムアウトは何秒ですか？How long is the visibility timeout?

  1. 120秒です。

    120 seconds.

  2. レンダー中は、20秒ごとにタイムアウトを延長しています。

    While rendering, the worker extends it every 20 seconds.

  3. なので、長いレンダーでもメッセージは見えないままです。

    So the message stays hidden even during a long render.

  4. ワーカーが落ちたら延長が止まり、2分以内に戻ってきます。

    If the worker dies, extending stops and the message is back within two minutes.

Show you extend a short timeout (ChangeMessageVisibility) rather than setting one huge timeout; a long fixed timeout means slow recovery after a crash.

FIFOキューは使わないんですか？Don't you use a FIFO queue?

  1. 使っていません。標準キューです。

    No, it is a standard queue.

  2. 順番は、レンダーでは重要ではありません。

    Order doesn't matter for renders.

  3. FIFOでも、ワーカーが落ちれば同じメッセージがまた届きます。

    Even with FIFO, the same message comes back if a worker dies.

  4. なので結局、ワーカー側を冪等(べきとう)にする必要があります。

    So the worker has to be idempotent in any case.

FIFO deduplication only covers sends within 5 minutes; it does not stop redelivery after a crash.

Where it lives in ReelWalk

  • apps/web/lib/queue.ts

    SendMessage with a body of only { jobId, generation }.

  • packages/db/src/outbox.ts

    The outbox: the message is written with the job in one transaction, then relayed to SQS (FOR UPDATE SKIP LOCKED).

  • apps/worker/src/index.ts

    ReceiveMessage with WaitTimeSeconds 10, MaxNumberOfMessages 1 and the visibility timeout.

  • docker-compose.yml

    ElasticMQ config: render-jobs, 120 s visibility, DLQ after 3 receives.

  • docs/adr/0001-sqs-for-render-jobs.md

    Why SQS over a Redis list, Postgres SKIP LOCKED or one Kubernetes Job per render.
