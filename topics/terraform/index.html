Terraform

インフラのコード化（IaC）

テラフォームBuilt and running

AWSのリソースを、コードで定義(ていぎ)して作るツールです。

It defines and creates AWS resources as code.

実装済(じっそうず)み Applied and live: remote state in S3 with lock files; the media bucket and CloudFront (imported), SQS with a DLQ, ECR, the GitHub OIDC role, the app IAM policy, a budget, the VPC, App Runner, the Fargate task definition and SSM parameters. EKS and RDS were created and destroyed the same day. CI scans infra/terraform with Trivy.

ExplainWhyWordsInterviewIn the repoWatch

How to explain it

  1. Terraform(テラフォーム)は、インフラをコードで書く、IaCのツールです。

    Terraform is an IaC tool: infrastructure written as code.

  2. HCLという言語で、欲(ほ)しい状態を宣言的(せんげんてき)に書きます。

    You declare the desired state in a language called HCL.

  3. planで差分(さぶん)を確認して、applyで反映(はんえい)します。

    plan shows the diff and apply makes the change.

  4. ReelWalkでは、S3、SQS、CloudFrontを定義しています。

    ReelWalk defines S3, SQS and CloudFront.

  5. RDSやECSも、プレースホルダーとして書いてあります。

    RDS and ECS are written as placeholders too.

  6. ただ、一度もapplyしていません。

    But it has never been applied.

  7. 初期の下書(したが)きなので、今の設計とずれています。

    It is an early draft, so it differs from the current design.

Why ReelWalk uses it

  1. 手作業(てさぎょう)の設定は、再現(さいげん)もレビューもできません。

    Manual setup can be neither reproduced nor reviewed.

  2. コードなら、プルリクエストで変更をレビューできます。

    As code, changes are reviewed in pull requests.

  3. 一方で、stateファイルを安全に管理する必要があります。

    On the other hand, the state file must be managed safely.

Interview questions

Terraform(テラフォーム)で、何を管理していますか？What do you manage with Terraform?

  1. メディア用のS3とCloudFront、SQSのキュー、ECR、GitHub用のIAMロールです。

    The S3 bucket and CloudFront for media, the SQS queues, ECR, and the IAM role for GitHub.

  2. App Runner(アップランナー)と、Fargate(ファーゲート)のタスク定義(ていぎ)、SSMのパラメータも管理しています。

    Also the App Runner service, the Fargate task definition and the SSM parameters.

  3. stateはS3に置き、planで差分(さぶん)を確認してからapplyしています。

    State lives in S3; I check the plan diff before every apply.

  4. EKSとRDSも一度作りましたが、コストの判断で削除し、ADRに残しています。

    I also created EKS and RDS once, deleted them over cost, and recorded it in an ADR.

It is live. Existing resources were imported, not recreated, so the CloudFront domain survived. The scanner findings (no WAF, no customer-managed key, public subnets) are accepted with reasons in .trivyignore.yaml.

今のTerraformの課題は、何ですか？What are the problems with the current Terraform?

  1. 初期に書いたので、今の構成(こうせい)とずれています。

    It was written early, so it no longer matches the architecture.

  2. ECSやRedisがありますが、今はKubernetesで、Redisは使いません。

    It has ECS and Redis, but we now use Kubernetes and no Redis.

  3. SQSのDLQも、まだ定義していません。

    The SQS DLQ is not defined yet either.

  4. stateは、S3に置いてロックする予定です。

    State is planned to live in S3 with locking.

  5. EKSとVPCの定義も、これから追加(ついか)します。

    EKS and VPC definitions still need to be added.

Self-critique is well received in Japanese interviews; it shows you know what 'done' looks like.

TerraformとHelmは、どう役割(やくわり)を分けますか？How do you split responsibilities between Terraform and Helm?

  1. Terraformは、AWSの土台(どだい)を作ります。

    Terraform builds the AWS foundation.

  2. VPC、EKS、RDS、S3、SQSなどです。

    VPC, EKS, RDS, S3, SQS and so on.

  3. Helmは、その上にアプリをデプロイします。

    Helm deploys the app on top of it.

  4. 変更の頻度(ひんど)が違うので、分けて管理します。

    They change at different rates, so they are managed separately.

Lifecycle separation is the key idea: infrastructure changes rarely, the app changes every release.

    Region, project and bucket name variables.

    Notes that the Terraform started as an ECS/Fargate design before Kubernetes was chosen.
