Trivy

脆弱性(ぜいじゃくせい)スキャン

トリビーBuilt and running

依存関係(いぞんかんけい)、設定、イメージの脆弱性(ぜいじゃくせい)をスキャンします。

It scans dependencies, configuration and images for vulnerabilities.

実装済(じっそうず)み Real: three Trivy scans (lockfile, config, images) gate every CI run at HIGH/CRITICAL; real findings were fixed in commits be7eb1c and c317ca1, and accepted ones are documented in .trivyignore.yaml.

How to explain it

  1. Trivy(トリビー)は、オープンソースのセキュリティスキャナーです。

    Trivy is an open-source security scanner.

  2. CIでは、三つのものをスキャンしています。

    In CI it scans three things.

  3. 一つ目は、pnpmのロックファイルの依存関係です。

    First, the dependencies in the pnpm lockfile.

  4. 二つ目は、DockerfileとHelmチャートの設定ミスです。

    Second, misconfigurations in the Dockerfiles and Helm chart.

  5. 三つ目は、ビルドしたwebとworkerのイメージです。

    Third, the built web and worker images.

  6. HIGHかCRITICALが見つかると、CIが失敗します。

    A HIGH or CRITICAL finding fails CI.

  7. 修正版(しゅうせいばん)がないものは、除外(じょがい)しています。

    Findings with no fixed version are excluded.

  8. 許容(きょよう)した指摘(してき)は、理由と一緒にファイルに残します。

    Accepted findings are recorded in a file with the reason.

Why ReelWalk uses it

  1. 脆弱性に、デプロイの前に気づけます。

    Vulnerabilities are caught before deployment.

  2. サードパーティのActionではなく、公式のイメージで動かしています。

    It runs from the official image, not a third-party Action.

  3. バージョンを、一か所で固定できるからです。

    That pins the version in one place.

  4. トレードオフは、直せない指摘でCIが止まることです。

    The trade-off is CI blocking on findings you cannot fix.

Interview questions

脆弱性が見つかったら、どう対応しますか？How do you handle a vulnerability when one is found?

  1. まず、本当に使われている部分かを確認します。

    First I check whether the affected code is actually used.

  2. 実際に、TrivyでHIGHとCRITICALが出たことがあります。

    Trivy actually did report HIGH and CRITICAL findings.

  3. 古いnpmのロックファイルが、脆弱(ぜいじゃく)なNext.jsを固定していました。

    A stale npm lockfile pinned a vulnerable Next.js.

  4. 使っていないファイルだったので、削除しました。

    It was unused, so I deleted it.

  5. Prismaが固定する依存は、pnpmのoverridesで上げました。

    Dependencies pinned by Prisma were raised with pnpm overrides.

  6. 最後に、CIがグリーンになることを確認しました。

    Then I confirmed CI went green.

This is a listed job duty. Use the flow: triage (used? fix available?) -> fix or remove -> verify in CI -> record any exception. Commit be7eb1c.

イメージのスキャンでは、何が見つかりましたか？What did the image scan find?

  1. 同梱(どうこん)されたnpmや、pnpmのストアに指摘がありました。

    There were findings in the bundled npm and the pnpm store.

  2. テスト用ツールが入れた、古いesbuildもありました。

    Also old esbuild builds pulled in by test tooling.

  3. どれも、実行時には使っていないものでした。

    None of it was used at runtime.

  4. なので、本番用の依存だけを入れるようにしました。

    So I made the image install production dependencies only.

  5. 使わないパッケージマネージャーも、消しました。

    And removed the unused package managers.

Removing what is not needed beats upgrading it: it shrinks the attack surface. Commit c317ca1.

すべての指摘を、直すべきですか？Should every finding be fixed?

  1. いいえ、リスクを見て判断します。

    No, I decide based on risk.

  2. 例えば、nginxのイメージがrootで動くと指摘されました。

    For example, an nginx image was flagged for running as root.

  3. でも、ローカルのCompose専用で、デプロイはしません。

    But it is only for local Compose and is never deployed.

  4. なので、理由を書いて、許容しました。

    So I accepted it with a written reason.

  5. 非rootのイメージへの切(き)り替(か)えは、課題として残しています。

    Switching to a non-root image is tracked as follow-up.

They are checking you do not silently suppress findings: every entry in .trivyignore.yaml has a statement, and the scan scope (skipping local-only and unapplied dirs) is commented in ci.yml.

Where it lives in ReelWalk

  • .github/workflows/ci.yml

    TRIVY_IMAGE pinned to 0.75.0; fs, config and image scans with --exit-code 1.

  • .trivyignore.yaml

    Accepted DS-0002 (root user) findings, each with a written statement: local nginx images, a backup Dockerfile, the GPU splat image.

  • package.json

    pnpm overrides for mysql2 and deepmerge-ts, transitive packages pinned by the Prisma CLI.

  • apps/worker/Dockerfile

    The fix for the image findings: --prod install and package managers removed from the runner.
