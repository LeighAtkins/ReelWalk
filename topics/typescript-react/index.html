A01

TypeScript + React

型安全(かたあんぜん)なUI開発

タイプスクリプト・アンド・リアクトBuilt and running

TypeScriptとReactで画面を作り、zodで外から来るデータを検証(けんしょう)します。

I build the UI with TypeScript and React, and validate incoming data with zod.

実装済(じっそうず)み Built and used everywhere: TypeScript across apps and packages, React 19 in the web app, zod 4 schemas in packages/core and in every Server Action.

ExplainWhyWordsInterviewIn the repoWatch

How to explain it

  1. フロントもサーバーも、TypeScriptで書いています。

    I write both the front end and the server in TypeScript.

  2. 画面はReactのコンポーネントで作っています。

    The screens are built from React components.

  3. ただ、型はコンパイル時(じ)にしかチェックされません。

    But types are only checked at compile time.

  4. なので、外から来るデータはzodで検証(けんしょう)します。

    So data coming from outside is validated with zod.

  5. タイムラインはJSONで保存していて、スキーマで形を確かめます。

    The timeline is stored as JSON, and a schema checks its shape.

  6. スキーマから型も作れるので、定義(ていぎ)は一か所で済(す)みます。

    Types can be derived from the schema, so the definition lives in one place.

  7. 編集の処理は純粋関数(じゅんすいかんすう)にして、packages/coreにまとめました。

    Editing logic is written as pure functions, collected in packages/core.

  8. だから、ブラウザがなくてもVitestでテストできます。

    That means it can be tested with Vitest without a browser.

Why ReelWalk uses it

  1. Webとワーカーで、同じ型とルールを共有(きょうゆう)できるからです。

    Because the web app and the worker can share the same types and rules.

  2. DBのJSON列(れつ)は型がゆるいので、読む時にzodで確かめます。

    JSON columns in the DB are loosely typed, so I check them with zod when reading.

  3. トレードオフは、スキーマを保守(ほしゅ)する手間(てま)です。

    The trade-off is the effort of maintaining the schemas.

  4. でも、壊(こわ)れたデータで画面が落ちるよりはいいと考えました。

    But I judged that better than the screen crashing on broken data.

Interview questions

なぜzodを使っているんですか？Why do you use zod?

  1. TypeScriptの型は、実行時には消えてしまいます。

    TypeScript types disappear at runtime.

  2. でも、ブラウザから来るデータは信用(しんよう)できません。

    But data coming from the browser can't be trusted.

  3. なので、Server Actionsの入口(いりぐち)でzodで検証(けんしょう)しています。

    So I validate it with zod at the entry of each Server Action.

  4. DBから読んだJSONも、同じスキーマで確かめます。

    JSON read from the DB is checked with the same schema.

  5. スキーマから型を作るので、型と検証がずれません。

    Types are derived from the schema, so types and validation never drift.

They want to hear that you know types are compile-time only. Mention z.infer: one source for both the type and the check.

エディターの状態は、どう管理していますか？How do you manage the editor's state?

  1. タイムラインはuseReducerで持っています。

    The timeline is held in a useReducer.

  2. 編集はすべて、packages/coreの純粋関数(じゅんすいかんすう)です。

    Every edit is a pure function from packages/core.

  3. undoとredoは、スナップショットのスタックで実装(じっそう)しました。

    Undo and redo are a stack of snapshots.

  4. スライダーの操作は、一回のundoにまとめています。

    A slider drag is merged into a single undo step.

  5. 再生中(さいせいちゅう)の時刻(じこく)は、Reactのstateに入れていません。

    The playback time is not kept in React state.

  6. 30fpsで再(さい)レンダリングしないためです。

    That avoids re-rendering the editor at 30 fps.

The playhead-outside-state detail shows real React performance experience. Say it if you have time.

anyはどのくらい使いますか？How much do you use `any`?

  1. 基本的には使いません。

    Basically never.

  2. 外から来る値は、まずunknownとして受け取ります。

    Values from outside are received as unknown first.

  3. それをzodで検証(けんしょう)してから、型の付いた値にします。

    Then zod validates them and turns them into typed values.

  4. saveReelのtimelineも、unknownで受けてからパースしています。

    saveReel also takes the timeline as unknown and then parses it.

unknown + parse is the answer they hope for. saveSchema in apps/web/app/actions.ts really does use z.unknown().

Where it lives in ReelWalk

  • packages/core/src/timeline.ts

    The zod timeline schema and the pure editing functions (split, trim, move).

  • apps/web/components/editor/editor.tsx

    The client editor: useReducer with an undo/redo history.

  • apps/web/components/editor/history.ts

    Undo/redo as a stack of timeline snapshots.

  • packages/core/tests/timeline.test.ts

    Vitest tests for the editing rules, no browser needed.
