Vitest

単体(たんたい)テスト

ヴィテストBuilt and running

ロジックを、速い単体(たんたい)テストで確認するツールです。

It checks logic with fast unit tests.

実装済(じっそうず)み Real: Vitest suites in packages/core, packages/render and apps/worker run in CI's verify job on every push.

ExplainWhyWordsInterviewIn the repoWatch

How to explain it

  1. Vitest(ヴィテスト)は、Viteベースの速いテストランナーです。

    Vitest is a fast test runner built on Vite.

  2. Jestと、ほぼ同じ書き方ができます。

    You write tests almost the same way as in Jest.

  3. ReelWalkでは、主(おも)にcoreパッケージをテストしています。

    In ReelWalk it mainly tests the core package.

  4. 書き出しジョブの、状態遷移(じょうたいせんい)が正しいかを確認します。

    It checks that render job state transitions are correct.

  5. キューのメッセージを、処理するか捨(す)てるかの判断もテストします。

    It tests the decision to process or discard a queue message.

  6. アップロードできるファイルの種類も、テストしています。

    It also tests which file types can be uploaded.

  7. workerのハンドラーは、DBやS3をモックしてテストします。

    The worker handler is tested with the database and S3 mocked.

  8. CIでは、turbo run testで全部のパッケージを実行します。

    CI runs every package through turbo run test.

Why ReelWalk uses it

  1. 判断のロジックを、純粋(じゅんすい)な関数に分けました。

    Decision logic is split out into pure functions.

  2. だから、DBやキューなしで、すぐテストできます。

    So it can be tested instantly without a database or queue.

  3. ただ、本物のChromeやSQSの動きは確認できません。

    But it cannot check real Chrome or SQS behaviour.

  4. そこは、PlaywrightのE2Eで補(おぎな)っています。

    Playwright E2E covers that.

Interview questions

どんな単体テストを書きましたか？What kind of unit tests did you write?

  1. 一番大事なのは、ジョブの状態遷移のテストです。

    The most important are the job state transition tests.

  2. 成功したジョブが、他の状態に戻らないことを確認します。

    They check that a succeeded job never leaves that state.

  3. 同じメッセージが二回(にかい)届(とど)いても、二回書き出しません。

    A message delivered twice is not rendered twice.

  4. 失敗したら、指数バックオフで再試行(さいしこう)することも確認します。

    They also check that failures retry with exponential backoff.

Tie it to idempotency: SQS is at-least-once, and the tests prove duplicates are harmless.

テストしやすくするために、工夫したことは？What did you do to make the code easy to test?

  1. 判断と副作用(ふくさよう)を分けました。

    I separated decisions from side effects.

  2. decideDeliveryは、何をするかを返すだけです。

    decideDelivery only returns what to do.

  3. DBの更新やS3は、ハンドラー側(がわ)で行います。

    Database updates and S3 happen in the handler.

  4. ハンドラーのテストでは、それをvi.fnでモックします。

    The handler tests mock those with vi.fn.

'Functional core, imperative shell' is the idea; you don't need the English phrase, just the split.

単体テストとE2Eは、どう使い分けますか？How do you divide work between unit tests and E2E?

  1. ロジックの組み合わせは、単体テストで網羅(もうら)します。

    Logic combinations are covered by unit tests.

  2. 速いので、ケースをたくさん書けます。

    They are fast, so I can write many cases.

  3. E2Eは、ユーザーの大事な流れだけにしています。

    E2E covers only the important user flows.

  4. 遅いので、数を絞(しぼ)っています。

    They are slow, so I keep them few.

This is the test pyramid; mentioning it by name (テストピラミッド) is fine.

Where it lives in ReelWalk

  • packages/core/tests/job-status.test.ts

    Allowed transitions: happy path, retries, SUCCEEDED is final, the worker cannot be skipped.

  • packages/core/tests/queue.test.ts

    decideDelivery (claim, duplicate, stale heartbeat), decideFailure exponential backoff, dead-letter handling.

  • packages/core/tests/uploads.test.ts

    Upload type resolution and object key rules.

  • apps/worker/tests/handler.test.ts

    handleDelivery and handleDeadLetter with vi.fn mocks: no double render, re-queue with backoff, DLQ on last attempt.
