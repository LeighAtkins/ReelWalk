Q02

Render worker

動画を書(か)き出(だ)すワーカー

レンダーワーカーRuns locally with a stand-in

キューからジョブを取り、Remotionで動画を作ってS3に置きます。

It takes jobs from the queue, renders the video with Remotion and puts it in S3.

ローカルで検証(けんしょう) Built and tested (Vitest handler tests, a real render in Playwright); it runs in Docker Compose and as 2 pods on kind against ElasticMQ and MinIO, never on EKS. In production the real AWS service is used (ADR 0011, 0015).

How to explain it

  1. ワーカーは、Webとは別のNode.jsのプロセスです。

    The worker is a Node.js process separate from the web app.

  2. SQSをロングポーリングして、1件ずつ受け取ります。

    It long-polls SQS and receives one message at a time.

  3. まずDBのジョブを見て、処理するかどうか決めます。

    First it looks at the job row and decides whether to process it.

  4. 条件付(じょうけんつ)きのUPDATEで、ジョブをRUNNINGにします。

    It claims the job by setting it to RUNNING with a conditional UPDATE.

  5. Remotionで、ヘッドレスChromeとffmpegを使って書(か)き出(だ)します。

    Remotion renders it with headless Chrome and ffmpeg.

  6. 20秒ごとに、タイムアウトを延長してハートビートを書きます。

    Every 20 seconds it extends the timeout and writes a heartbeat.

  7. MP4をS3に上げてSUCCEEDEDにし、メッセージを消します。

    It uploads the MP4 to S3, sets SUCCEEDED and deletes the message.

  8. 1つのPodでは、同時に1本だけレンダーします。

    Each pod renders only one job at a time.

Why ReelWalk uses it

  1. レンダーはメモリを数GB使い、Webとは負荷(ふか)の形が違います。

    A render uses gigabytes of memory; its load looks nothing like the web app's.

  2. 分けておけば、レンダーが落ちてもサイトは止まりません。

    Kept apart, a crashing render never takes the site down.

  3. 1Pod1本なので、メモリの見積(みつ)もりが簡単です。

    One render per pod makes memory easy to size.

  4. その代わり、処理量はPodの数で増やすしかありません。

    The trade-off is that throughput only grows by adding pods.

Interview questions

レンダー中にワーカーが落ちたら、どうなりますか？What happens if a worker dies mid-render?

  1. タイムアウトの延長とハートビートが止まります。

    Extending the timeout and the heartbeat both stop.

  2. 120秒後に、メッセージがまた見えるようになります。

    After 120 seconds the message becomes visible again.

  3. 別のワーカーが受け取り、ハートビートが古いので引き継ぎます。

    Another worker receives it and takes over, because the heartbeat is stale.

  4. 出力は同じキーに上書(うわが)きなので、動画は1本のままです。

    The output overwrites the same key, so there is still one video.

Quote the timing chain: heartbeat 20 s < stale 60 s < visibility 120 s. config.ts refuses to start otherwise, so a redelivery is never wasted on a 'defer'.

デプロイ中のレンダーは、どうなりますか？What happens to a render during a deploy?

  1. SIGTERMを受けたら、新しいメッセージは取りません。

    On SIGTERM it stops taking new messages.

  2. 今のレンダーは、最後まで続けます。

    It carries on with the current render.

  3. 猶予(ゆうよ)は300秒にしています。

    The grace period is 300 seconds.

  4. 間に合わなくても、タイムアウト後に別のPodがやり直します。

    If it runs out, another pod redoes the job after the timeout.

This is graceful shutdown plus at-least-once as a safety net. Saying both shows you thought about rollouts, not just happy paths.

なぜ1つのPodで1本だけなんですか？Why only one render per pod?

  1. Chromeのレンダーは、メモリをたくさん使います。

    Rendering in Chrome uses a lot of memory.

  2. 1本に限れば、リソースの上限を決めやすいです。

    Limiting it to one makes resource limits easy to set.

  3. 1本の中では、Chromeのタブを4つ並列で使います。

    Inside one render, it uses four Chrome tabs in parallel.

  4. 今のHPAはCPUベースなので、キューの長さで増やすのが改善点です。

    Today's HPA is CPU-based; scaling on queue depth (KEDA) is the planned improvement.

HPA is off by default in values.yaml and KEDA is only planned. Say 改善点 / 予定, not 使っています.

Where it lives in ReelWalk

  • apps/worker/src/index.ts

    Poll loop, /healthz liveness endpoint and SIGTERM handling.

  • apps/worker/src/handler.ts

    handleDelivery: decide, claim, heartbeat, render, succeed or retry.

  • apps/worker/src/config.ts

    Checks heartbeat 20 s < stale 60 s < visibility 120 s at startup.

  • infra/helm/reelwalk/templates/worker.yaml

    Deployment with a 300 s grace period, /dev/shm for Chrome, optional CPU HPA.
